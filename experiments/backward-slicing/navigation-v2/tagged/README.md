## 原程序及变异执行

每组预定三次，先要求原程序全部参数行通过。最后两列按轮次列出各自对三个固定变异的检出数。缺表示未交付或原程序未全过，原因在逐轮回执中。

| 案例 | 原程序全过 Base / v2 | Base 三轮检出数 | v2 三轮检出数 |
|---|---|---|---|

以全部 21 次尝试为分母，Base 原程序全过 18/21，v2 为 19/21。Base 已交付但原程序未通过的两份代码来自 Ansible 和 Flask，均在按既定相对缩进注入后触发 unexpected indent。仅统计两组同例同轮都通过原程序的 16 对，每对比较相同的三个变异，Base 检出 37/48，v2 检出 43/48。逐对为 v2 多检 5 对、相同 10 对、少检 1 对。仅比较双方可执行的轮次会排除交付失败，须与全 21 次交付和可执行性共同阅读。

Langflow 两个可配对轮次中，Base 检出遗漏设置查询，v2 还检出解密参数改变与重复解密。v2 候选验证了 decrypt_api_key 的实参与次数。Jib 三个 Base 均漏掉重复 createLayers，v2 三次中只捕获一次。Ansible 的重复探测可因有限的 Stub side_effect 耗尽而暴露；两个实验组的合格候选各轮均有两项显式断言检出，第三项是否被检出取决于 Stub 耗尽。Click 两例的双方合格轮次检出数相同。三次重复和目的抽取的七例不足以推出 165 例总体效果。
