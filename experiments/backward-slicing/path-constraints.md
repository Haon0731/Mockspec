# 在后向切片上增加近似路径约束：方案调查

日期：2026-11-04。承接[首次探索](README.md)，回答“数据流与路径约束能否帮助 Agent 推断 Mock”。本文保留方案调查阶段的推导；随后已完成[三组快速实验](path-pilot/README.md)，包含新的生成、真实Java/Python执行与有限路径见证。该实验未引入SMT或升级生产能力，且未证明逐方法摘要提高Mock质量。

## 判断

**可以，建议下一步研究“测试目标导向的切片＋带条件的值传播和调用效果”。** 分析层先组织少量候选场景、识别明显矛盾和缺失证据，Agent 再据此选择并具体化 Mock。无需先建完整形式化规格，也无需一开始就做全仓符号执行。

前一轮并未证明“只靠切片不行”：现有原型既有漏边也有多报，尚非完整数据依赖切片。补路径条件不能修复漏掉的调用关系，Flask A 的只读方法 patch 错误也不是路径不可行问题。新方案针对的具体缺口是：**依赖关系相关，不代表这些关系能在同一条执行中同时成立；知道值来自哪里，也不代表已经知道它经过什么变换。**

## 1. Mock 与数据流的关系

| 对象 | 需要追踪的关系 | 可推断的内容 |
| --- | --- | --- |
| Stub 返回值 | 依赖结果→局部/字段→转换→分支/输出 | 返回对象的哪些字段、值域、字符串结构影响测试目标 |
| 抛异常 | 调用结果模式→异常出口/handler→后继是否执行 | 哪个依赖可抛什么类型的异常，是否应阻止后续调用 |
| 有状态 Mock / void 调用 | 写入→别名/后续读取→输出 | 要改变什么可见状态，后一次调用是否依赖前一次调用 |
| 参数断言 | 输入与中间值→依赖调用实参 | 原样传递、转换、筛选、参数对应关系 |
| 次数、顺序、不调用 | 调用事件→路径、循环、早退、异常、重试 | 某个已选场景中的事件轨迹或次数范围 |

因此应同时保留数据关系、控制/异常关系与状态关系。一个没有返回值的 `send()` 可能正是测试目标；一个影响缓存状态的调用也可能通过下一次读取起作用。

Mock 行为在此表示**测试选择的外部响应**，不是恢复不可见真实实现。选择应与可见代码、接口约束和测试目标一致；依赖真实业务语义未知时仍需保留未知。

## 2. 直接相关的研究依据

以下是重点阅读的近邻，不是穷尽性新颖性审查；没有把论文覆盖率提升转写为本项目收益。

| 工作 / 状态 | 已有机制 | 对本研究的启示与边界 |
| --- | --- | --- |
| *Mock-object generation with behavior*，ASE 2006，方法/原型 | 根据单元测试中 Mock 的使用进行 .NET 符号执行，生成行为；不要求存在真实被替代实现 | 直接说明“在未知实现边界反推 Mock 行为”有先例；不是现成 Java/Python masked-test Agent 工具。[作者机构页面](https://www.microsoft.com/en-us/research/publication/mock-object-generation-with-behavior/) |
| *Joining Dataflow with Predicates*，ESEC/FSE 2005，方法 | 用谓词划分状态，分别保存数据流事实，避免不同路径过早合并；必要时细化谓词 | 支持“条件化的数据流”而非把一组 guard 附在不区分路径的图后面。[作者论文](https://ranjitjhala.github.io/static/joining_dataflow_with_predicates.pdf) |
| *Path-Sensitive Backward Slicing*，SAS 2012，方法 | 用符号执行排除不可行路径依赖，复用等价子问题；循环使用近似不变式 | 切片与路径约束结合已有成熟思想，仍需应对路径爆炸；不能把这篇 C 分析结果直接当作本仓跨语言支持。[作者论文](https://jorgenavas.github.io/papers/BackwardSlicing-SAS12.pdf) |
| CONBRIO，ICSE 2018，方法/工具 | 使用相关可见函数构成 extended unit，再结合 symbolic calling contexts 过滤不合理单元执行 | 任意 symbolic stub 可能造成不真实的上下文；论文的简化 stub 不更新全局/输出参数，不能视作完整状态 Mock 方案。[论文§2–3](https://swtv.kaist.ac.kr/files/publications/international_conference/3180155.3180253.pdf) |
| SymPrompt，PACMSE/FSE 2024，方法 | AST 收集近似路径条件与返回表达式，保留不能解析的调用，选覆盖新分支的路径，再由 LLM 生成测试 | 最接近“程序分析给条件、Agent 做具体推理”的轻量起点。主要目标是方法覆盖，不是证明跨过程 Mock 交互正确；论文版本称实现为研究原型，不据此保证公开可复用代码。[论文§3.2–3.4](https://arxiv.org/html/2402.00097v2) |
| PALM，2025首发、2026-02更新的 arXiv v2，预印本/工具 | AST 路径枚举，将路径条件嵌入可执行程序变体中的断言，LLM 生成测试并验证路径 | 说明可以用执行确认路径而不翻译全部库为 SMT；借鉴验证方式时须保持本项目普通测试和基线程序身份，不把加断言的变体当原程序。[论文记录](https://arxiv.org/abs/2506.19287v2) |

CONBRIO 的目标包括排除系统上下文不可行的单元执行。本项目不能据此去读取被隐藏依赖，或禁止隔离测试本来允许的外部响应；可复用的是“保留可见上下文约束”的原则。

潜在贡献应落在**测试目标、未知依赖边界、跨过程值与事件关系、多合法场景、交互断言质量**的结合上。“切片＋路径条件”或“路径条件＋LLM”本身已有直接先例。

## 3. 推荐机制

```mermaid
flowchart LR
    T[测试观察目标] --> S[后向切片选择相关代码]
    S --> P[在原控制流上提取有界路径]
    P --> C[条件化值传播与调用效果]
    C --> V[轻量矛盾检查／可选局部SMT]
    V --> A[Agent选择场景并生成Mock]
    A --> E[原测试与交互故障验证]
    E -->|发现具体缺口| P
```

### 3.1 目标在前，切片限制分析范围

从普通断言、预期异常、MUT输出及相关调用事件开始。缺失的 Mock Assertions 不能作为唯一种子；先找到可能相关的依赖交互，再由测试目标决定哪些值得验证。

切片用于选择相关代码和调用链。**路径必须沿原 CFG/异常边恢复，不能把候选依赖图上的一串边当执行路径。** 被切掉的中间代码要通过可靠摘要跳过；没有摘要的异常或状态效果不能直接删除。当前 Spoon/AST 原型仍缺真实 CFG/可靠调用解析，这是实现前置缺口。

第一版只展开目标相关的少量分支；跨过程追踪可见 helper 并保留调用上下文。循环/递归使用明确的有界展开或已验证摘要，超过界限记录未探索范围。`0/1/many` 可以是粗略描述，不能自动证明精确次数。

### 3.2 未知依赖作为每次调用的符号事件

对每次依赖调用记录：

```text
调用位置 + 接收者身份 + 本次调用序号
实参表达式
结果：normal(返回值) 或 raise(异常)
可能写入：已知相关位置 / 未知
来源、假设、支持范围
```

不同调用默认使用独立符号，并保留可能的状态关联；不能因为方法名、参数相同就强制同返回值。只有已知纯性/确定性或显式选择这种 Stub 策略时，才用共享未解释函数表示同输入同输出。

正常/异常两种结果各自也可带状态写入：方法可以先写状态再抛异常。未知写入要使可能受影响的旧事实失效；若别名范围不清楚，则保留 `unknown`，而不是假设无副作用。这里没有承诺完整 heap 求解。

### 3.3 同时携带三类约束

- **路径条件**：某个比较、判空、分支极性、前置调用正常完成。
- **值与状态关系**：赋值、实参到形参、返回到调用结果、字符串/字段变换；不同路径不能把互斥的两个赋值无条件合取。
- **目标关系**：输出与测试断言相符、异常属性满足普通测试、选定交互事件有证据支持。

对固定测试输入 `I`、调用响应/效果 `M`、局部状态 `L` 和路径 `π`，概念上考虑：

```text
I ∧ visible_semantics(π, L, M) ∧ guards(π) ∧ test_goal(L, M)
```

多个候选路径之间是“或”，不是要求所有分支同时成立。局部变量只是连接证据的中间量，不必全部暴露给 Agent。这个表达式是方案说明，并不要求第一版生成完整可求解公式。

### 3.4 先用有限约束域，必要时局部求解

优先支持 nullness、布尔/枚举、常量等式、简单整数区间、已知字符串常量/拼接、明确的 normal/raise。常量传播、等式合并和区间交就能发现部分矛盾，**可靠的局部剪枝不必依赖 SMT**。

有实现先例：Clang 的 `RangeConstraintManager` 跟踪简单符号相等/不等与区间；`Z3CrosscheckVisitor` 再对报告约束做 SMT 复核。这支持分层检查的工程思路，但 Clang 本身不是我们的 Java/Python 后端。[区间实现](https://clang.llvm.org/doxygen/RangeConstraintManager_8cpp_source.html)；[Z3复核实现](https://clang.llvm.org/doxygen/Z3CrosscheckVisitor_8cpp_source.html)。

关系复杂但仍在受支持理论内时，再把局部片段交给 Z3/cvc5。Java有界整数与Python整数、溢出、字符串/URI归一化、异常等语义须由前端正确建模；不能用一个数学整数或任意字符串方程代替全部语言行为。

对未支持调用可以保留表达式原文交 Agent 理解，但不能将模型猜测的摘要当成已验证前提参与硬剪枝。

## 4. 用现有真实案例说明新增信息

以下是根据已留证源码做的人工推导示例，不是新分析器自动输出或本轮实验结果。

### Flask：应区分三种候选路径

对应 `helpers.py:282–285`：

```python
if (ctx := _cv_app.get(None)) is not None:
    ctx.app.aborter(code, *args, **kwargs)
_wz_abort(code, *args, **kwargs)
```

| 路径 | 响应条件（还需此前操作正常完成） | 事件后果 |
| --- | --- | --- |
| A | lookup正常返回None；fallback抛出满足当前普通断言的异常 | app.aborter不执行；fallback执行 |
| B | lookup正常返回非None；对象访问有效；app.aborter抛出满足断言的异常 | app.aborter执行；fallback不执行 |
| C | lookup返回非None；对象访问有效；app.aborter正常返回；fallback抛异常 | 两个调用都执行 |

第三条不能因为文档习惯或一个 `if` 就删掉。当前测试若只检查异常消息，某些配置可能使第三条也通过；仍要由测试意图选择合理场景，不能宣称A/B是全部合法答案。

若Agent选择B，才有依据配置aborter异常，并生成“fallback未调用”的**场景内断言**。不能把它推广成所有非空上下文下fallback都不调用。次数为一次也依赖该函数的直线调用结构、所选路径和相关控制流完整，而不是来自静态调用点计数。

路径条件无法解决 `ContextVar.get` 只读。Mock框架可替换位置、绑定方式、类型/final属性是另一个证据维度；要继续单独检查。

### CloudFoundry：不只要 `hasText`，还要输出构造关系

父类196–205行可组织成两种响应方案：

```text
health路径：hasText(r_health) → mapped_path = r_health
status路径：¬hasText(r_health) ∧ hasText(r_status) → mapped_path = r_status
```

还必须保留147–155行的关系：

```text
expected_health_url = URI_Builder(management_base, "/", mapped_path)
```

上一轮B给出`health`，并假设另一条management URL路径会补上`actuator`。单加 `hasText("health")` 仍会接受这个错误候选。保留值构造关系才能暴露“哪里贡献了`actuator`”这个缺口。

`URI_Builder` 不能未经核实就改写为普通字符串连接，`hasText` 也不等于单纯非空：空白字符等行为需要库摘要。对无可信摘要的情况，先给Agent精确调用链与待确认关系，标为unknown；需要自动验证时再加入经独立验证的最小库摘要。库摘要与未知Mock响应必须分开，不能为使候选成立临时编造。

## 5. 近似结果如何解释

| 分析状态 | 允许的结论 |
| --- | --- |
| 已证明冲突 | 若编码对该路径片段是精确或保守过近似，矛盾足以排除该片段中的候选；不能排除其他路径或未展开迭代 |
| 暂未发现冲突／solver SAT | 在当前抽象与假设下存在赋值或尚未检出矛盾；还不是可执行Mock或真实依赖行为的证明 |
| unknown／超预算／不支持 | 交回缺失证据和可能影响，不转换为“无调用”“无副作用”或“路径失败” |
| 执行见证 | 具体Mock在固定原测试与观测条件下执行成功；仍不证明所有等价场景或全局正确性 |

当前图既多报又漏报，不能假装它已经是保守过近似。对这种启发式图，即使SMT返回UNSAT，也只说明那组编码自相矛盾，不能给真实程序的全局不可达结论。

可行路径也不自动决定“哪些交互值得断言”。调用可能是实现细节；是否生成精确次数/顺序断言还需结合测试意图和合理替代实现。第一版优先直接参数关系、选定异常出口与有依据的不调用，避免全面 `verifyNoMoreInteractions`。

## 7. 最小下一步与判断标准

**建议先做“条件与值/事件摘要工具”，再决定是否加求解器。** Agent按测试目标请求局部证据，得到候选路径、相关依赖响应关系、已发现矛盾和unknown；它仍负责自主选择场景、补充取证和生成Mock。

第一阶段以Flask的三种事件路径、CloudFoundry的两种映射路径为机制校验；先修复/确认控制流与调用目标，再提取约束。JarFiles缺边作为前端失败单列，不交给求解器掩盖。源码库摘要只对实际遇到且影响结论的操作补充。

正式效果对照固定相同可见源码、基础模型和总预算，依次比较：

1. 仅切片原文。
2. 同原文＋guard。
3. 同原文＋guard＋值传播＋异常/事件摘要。
4. 第3组＋局部矛盾检查；需要时再单列SMT增量。

这样可以判断收益来自多看代码、路径提示、关系组织，还是机械一致性检查。现有两例用于开发，不作为泛化证明；在新增审核任务上多次配对生成，分别测原测试通过、交互故障检出、合法替代场景误拒绝、unknown比例、分析与模型成本。只有基线测试先通过的候选才能计变异检出。

预期最有希望改善的是：把互斥分支条件拼在一起、遗漏normal/throw造成的后继变化、忽略返回值加工和跨调用状态关联。是否实际改善仍待实现与对照；它不会自动修复patch API错误、缺失调用边或测试意图不明确。
