# Jib 导航表示与事实消融

本实验检验 #35 单例中的两个假设：导航要求模型频繁按 ID 查表；精简投影省去了可能帮助理解守卫或状态的事实。使用同一遮蔽测试、173 条关系、19 个观察、源码权限、模型和输出格式。每种表示各生成三次。先做四组表示 × 字段对照，再单独登记两组直接展示对照。各轮使用全新上下文。旧 #35 的三次生成不并入这次样本。[四组协议](protocol.md) · [直接展示协议](supplementary/protocol.md)

| 布局 | 精简字段 | 补回字段 | 模型看到的表示 |
|---|---|---|---|
| 原 C | OC | OR | 独立的观察表、事实集合和事实表。OC 的完整提示与 #35 原 C 字节一致。 |
| 按观察归组 | PC | PR | 每个观察下列出守卫、调用、正常返回及异常的摘要。端点详情仍在共享事实表。 |
| 直接展示 | DC | DR | 在可见断言旁显示已归属于该观察、端点或紧凑详情中出现目标词的关系。完整事实以字符串字典保存。 |

四种新表示均能机械还原具有相同字段的原始事实包。R 组从完整 B 恢复 10 条关系的谓词产生者和 3 条关系的 setter 链。DC 与 DR 卡片选取相同的事实 ID。对 base-image 观察，直接卡片分别列出 getFrom 的值到 getBaseImage() 的值流，以及 getJavaVersion 分支到同一观察的控制依赖，并保留各自的模态；没有证据将两者认作一条连续可行路径。卡片的词匹配只决定突出哪些已有边，不能增加语义证据。19 张直接卡片一共突出 117 条不同关系（含跨卡重复共 161 次）；其余关系仍在可逆的完整证据中。该表示同时改变组织方式、显著性和编码长度。[四组结构证明](inputs/proof.json) · [直接展示结构证明](direct-inputs/proof.json)

## 复现

在仓库根目录使用项目虚拟环境。重新构造输入和比对完整提示不调用模型。

```bash
study=experiments/backward-slicing/issue35/jib-navigation
replay=$(mktemp -d)
.venv/bin/python "$study/study.py" prepare --inputs "$replay/base"
.venv/bin/python "$study/study.py" prepare --direct --inputs "$replay/direct"
diff -qr "$study/inputs" "$replay/base"
diff -qr "$study/direct-inputs" "$replay/direct"
```

运行 study.py run 会发起新的模型调用。候选先按轮次和组别冻结，再使用 #35 的固定 Jib 容器、原程序、三处变异和审阅准则。评阅者只读匿名槽位。逐行回执、模型返回、工具调用和每轮用量分别保存在 evaluation、direct-evaluation、run 与 direct-run 下。

| OC 原布局、精简 | 322,662 | 102,913 | 2 / 3 / 2 | 207,922 / 323,684 / 208,767 |
| PC 按观察归组、精简 | 602,191 | 190,670 | 3 / 6 / 3 | 384,042 / 579,696 / 383,561 |
| OR 原布局、补回 | 339,285 | 107,514 | 2 / 6 / 3 | 218,591 / 449,645 / 217,340 |
| PR 按观察归组、补回 | 618,814 | 195,271 | 3 / 7 / 4 | 597,664 / 791,037 / 807,438 |
| DC 直接展示、精简 | 246,611 | 83,514 | 6 / 4 / 6 | 259,495 / 440,230 / 260,396 |
| DR 直接展示、补回 | 255,231 | 85,839 | 8 / 3 / 4 | 266,533 / 174,968 / 262,293 |

PC 在每张卡重复带入多条共享关系的摘要。两个字段条件下，按观察归组均增加了初始输入，而且三轮累计输入都高于相应的原布局。DC 对共享字符串去重，在断言旁展示有关边，首轮输入较 OC 少 19,399 token（18.9%）。DC 的三轮累计输入仍都高于 OC；补回字段时，DR 与 OR 的累计成本方向不一致。三轮均使用独立上下文和默认采样，工具调用数量与调用轮数也会影响累计成本。

## 执行结果

| 组 | 候选交付 | 原程序通过 | 检出同例变异 |
|---|---:|---:|---:|
| OC | 2/3 | 2/3 | 两个合格候选均 3/3 |
| PC | 3/3 | 3/3 | 三个候选均 3/3 |
| OR | 3/3 | 3/3 | 三个候选均 3/3 |
| PR | 3/3 | 3/3 | 三个候选均 3/3 |
| DC | 3/3 | 3/3 | 三个候选均 3/3 |
| DR | 3/3 | 3/3 | 三个候选均 3/3 |

OC 第三轮在 JSON 末尾缺少分隔符，按预登记规则保留为生成失败且未重试。其余 17 个候选均在固定 Jib 原程序上通过，并检出 `omit_create_layers`、`omit_compute_entrypoint` 和 `duplicate_create_layers` 三个变异。所有可执行候选的七项 F_stub 均匹配。静态盲评记录的额外交互限制仍然普遍存在：DC 第一轮比同轮 OC 多 10 项，其余 direct 候选为 12 项；直接边表示没有改善这个问题。

这组单例支持一个更窄的结论。按观察归组的 PC/PR 没有出现行为退化，但代价是重复事实和更高输入成本。直接边 DC/DR 将初始输入降到低于 OC，并保持 3/3 交付、原程序通过和变异检出。补回 `predicate_producers` 与 `setter_chain` 在 OR/PR/DR 中没有带来可区分的执行收益。三个重复只观察到 OC 的一次格式失败，无法证明布局稳定性已有总体提升。[四组执行回执](evaluation/execution.json) · [直接边执行回执](direct-evaluation/execution.json) · [逐轮对照](results.json)

## 行为结果

18 次独立生成交付 17 个候选。原布局、精简字段（OC）第 3 轮返回无效 JSON；其余候选全部通过原程序，全部检出 3/3 个预登记交互变异，匿名评阅均命中 7/7 项 Stub 判据，均覆盖两个参考交互。OC 第 1 轮有 2 项超出可见测试目标的交互限制，其余 16 个候选各有 12 项，包括要求处理器只查询一次 Java 版本等。该场景需要得到正确的基础镜像或入口点，但相同结果可以通过不同的查询次数得到。

因此，这个案例支持“导航的组织方式影响输入与探索成本”，没有观测到“补回谓词和 setter 细节即可改善 Stub、变异检出或额外交互限制”。原布局下成功交付的候选已达到预登记行为指标上限，两种字段、三种布局都未消除过度验证。一次 JSON 格式失败不足以解释某种版式对交付稳定性的因果作用。直接展示兼有词匹配突出和字典压缩，实验未单独分离这两种变化，也不覆盖 #35 中 Python 的槽位缩进问题。
