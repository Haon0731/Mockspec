# 后向分析断裂：根因与修复验证

日期：2026-11-11。范围：既有冻结输入、Flask 异常观察、Java 未知效果机制与 Jib 规模诊断。
不运行目标测试，不读取隐藏 Mock 答案，不改数据集；本记录不代表165例正式复跑。

## 已确定的根因

1. **Python 的库边界缺失。** 被测函数的 exceptional exit 与测试的调用点可定位，
   但一般数据流不会自动表达 `pytest.raises` 抑制异常、填充 `ExceptionInfo.value` 的语义。
   仅连接产品内部异常节点不足以说明断言受其影响。修复需要有来源的库摘要，
   与调用绑定、异常退出、捕获对象值流及断言可达性联合验证。
2. **Java 未知效果与执行条件缺失。** 摘要选择器必须在 WALA builder 初始化之后安装；
   早先只有候选目标、实际却是空 IR。修复选择器后，字段自写回仍不能代表未知值写入。
   另一个独立问题是：正常返回控制后续执行，不一定对应一条 SDG 正常出口依赖边。
   应联合真实摘要 IR、同调用点 CFG、同对象区域堆依赖验证，不能因缺少单条 SDG 边断言无影响。
3. **Jib 的传递堆集合膨胀。** 完整调用图共有13,086节点，其中JDK为12,622、
   Application为17、Extension为447。实际 OOM 出现在 WALA 构建跨过程堆依赖期间。
   全图每调用点的传递 Mod/Ref 基数之和为708,886,880；这是压力上界指标，
   不是实际切片节点数。最高压力集中在类初始化链。

## 已排除的简单修法

- 只保留入口向前可达调用图：节点降到11,144，但 FULL/FULL 切片仍 OOM。
- 用任意自定义 PointerKey 合并 JDK 堆：WALA 的 HeapExclusions 不识别该类型，
  可能跳过依赖或抛错。首次尝试已失败，不能把降低 Mod/Ref 基数当成正确性证据。
- 增加同名候选、仅看调用目标数量、只看无 OOM，均不能证明目标关系已恢复。

## 修复方案与验收约束

- Python：限定支持的 `pytest.raises` 形状，核验摘要参考源码；异常必须能从被测函数
  和精确测试调用逃逸，捕获变量必须真实流向同一个观察。内部吞异常、覆盖捕获、
  不匹配异常类型、同名伪函数应拒绝。参考宿主 pytest 版本不能冒充冻结项目依赖版本。
- Java 未知调用：显式未知效果 token，保留未知写、返回别名与正常／异常出口。
  堆证据绑定调用点、上下文、字段和对象区域；执行条件使用精确调用点 CFG。
  可达关系只证明可能影响，不证明路径可满足或一定写入某值。
- Jib：在完整调用图和指针分析之上试验 JDK 堆区域合并；保留应用字段区分。
  合并区域必须被 WALA 识别，并用弱更新保留所有可能写入。先验证真实 heap-data 边，
  再衡量固定2 GiB／180秒预算下成本。诊断入口与原始测试观察始终分开报告。

## 本轮已取得的结果

- [Python 异常观察](../python-exception-model-20261111-r2/report.md)：真实 Flask 的
  282／283／285 行异常源分别连接到120／126行断言，共6条可能影响关系；
  同时关联102行的 raises 观察。三个原观察均有对应证据，具体异常类型和文本仍未知。
  宿主 pytest9.1.1参考源码已核验，冻结项目依赖版本仍未知。
- [Java 未知效果](../issue23-unknown-effects-20261111/report.md)：首轮验收器报告4项有界机制通过，
  包括未知值写入、返回别名及 fresh 分支、正常完成到选定观察、抛异常前写入到处理器读取。
  两项错误调用／错误返回位置变异被拒绝，相关12项回归通过。但独立复核发现
  未知 token 与具体字段写入、criterion 方法／上下文、具体写入到具体 throw 的
  支配证据仍可能串接过宽，必须修正后重新验收；首轮绿色不能作为最终通过。
  fresh与实参在当前PA中仍合并，receiver／global／escaped等区域尚不覆盖。
- [独立复核后修正版](../issue23-unknown-effects-20261111-review-rev/report.md)已关闭上述三处假绿：
  token必须流向所选字段的同一写入，观察种子必须匹配caller/context/index，
  所选写入和匹配throw必须有明确的SSA支配对。新真实证据中4项机制与4项阴性均通过，
  12项回归通过，独立复核接受；旧失败与旧报告原样保留。
- 入口和契约相关51项回归通过；255项受保护历史产物哈希未变。
- 修正后的运行时区域 key 已通过独立 FULL/FULL 实测与复核：多个合并写保守到达读取，
  应用字段 x／y 仍区分，四种运行时堆位置形式共用区域，入口上下文唯一选择。
  压力指标降至3,078,905，但180秒内仍不能完成 FULL 切片；这是有效的成本改善，
  尚不是 Jib 分析完成。

## Jib 的可运行成本方案

最终诊断采用 WALA 自带 `CISlicer`：底层 SDG 不构造 heap 参数节点，
再由逐语句 Mod/Ref 构造上下文不敏感的堆 may-dependence，控制选项保持 FULL。
这与直接关闭堆分析不同；无 IR 调用仍需显式未知边界。
[WALA 1.7.2 源码](https://github.com/wala/WALA/blob/v1.7.2/core/src/main/java/com/ibm/wala/ipa/slicer/thin/CISlicer.java)
明确将该实现称为原型，故必须通过本项目的关系反例和真实成本验收，不能仅以工具名保证正确性。

**实际选择保留原始 WALA 堆位置，不合并运行时区域。** 合并在 FULL 模式下减少参数压力，
但在 CI 模式下会让大量运行时读写互相连接；不能把一种优化无条件用于另一种表示。
完整 CG／PA 建立后，仅对入口前向可达图切片，入口之前的初始化和外部调用者保持未知。

[r7 紧凑结果](../issue23-jib-ci-original-20261111-r7/summary.json)绑定完整原始产物的 SHA：

- 固定2 GiB Java堆／180秒限制；分析进程35.78秒，含编译37.10秒。
- 最大RSS为1,584,976 KiB（约1.51 GiB）；内部切片计时10.56秒。
- 完整调用图13,086节点，入口可达图11,144；指针分析保留4,852个实例键。
- 切片324,890个语句节点，按 Application 方法身份统计其中125个属于应用：
  `JarFiles.toJibContainerBuilder` 108个，诊断入口17个。
- 这是 whole-plan return 的 `diagnostic_override`，尚未映射原测试逐条断言。
  native／无 IR 效果仅保留未知声明，尚未验证逐调用边界；覆盖写和跨调用路径可能被保守保留。

原始切片 JSON 约121 MB，紧凑结果只提取应用节点与成本，不能当成完整切片。
CI 配置跳过冗余的全图压力预计算；旧字段的0值不是测得零压力，紧凑结果将其归一化为null。
进程墙钟含序列化，内部切片计时不含最终JSON序列化。资源门诊断通过不等于真实Jib观察验收通过。

复现使用 `wala-pilot/run_scale_diagnostic.py`，从 r7 的 `pre-registration.json` 取原始四个
输入参数，指定 `--entry-scope --ci-heap`、已有WALA classpath文件与新的输出目录。
不使用 `--runtime-region`。r5／r6是显式人工终止的配置探索，不计超时或成功；原始收据保留原因。

正式165例对照仍等待原始观察映射和未知边界验收，当前没有启动。
