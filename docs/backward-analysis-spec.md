# 目标相关后向分析与条件化行为规格

状态：实施与验收规格，尚未实现或完成验收。读者为分析器实现者、独立审查者和后续规格消费者。
本文件是该研究接口与验收语义的唯一说明，依据 [ADR-0002](adr/0002-mock-oriented-backward-evidence.md)；
真实案例见[验收清单](../experiments/backward-slicing/spec-acceptance.md)，现有实现见[差距表](../experiments/backward-slicing/spec-gaps.md)。
它不替换生产 [Scenario Contract](scenario-inference.md)，也不将历史关系自动升级为已验证规格。

## 1. 目标与边界

从冻结测试目标向后定位相关逻辑，在声明的程序边界内组织完整的候选执行解释，推导条件化依赖行为约束。
规格由共同约束、条件化分支、证据与未知组成，并记录探索覆盖情况。
不要求唯一解释、穷尽路径、求解全部外部响应或给出唯一 Mock 实现；不依赖 SMT。
复杂表达式原样保留；表达式不可求解不妨碍交付条件式规格，但会限制其实现可用性。

本轮范围是分析及规格接口、证据机制与研究验收。Mock 代码生成、目标测试执行、缺陷变体、Agent 对照不在本轮。
LLM 可作为未来约束推理消费者；本规格不以运行该阶段为完成条件，也不预设其推测具有程序证据等级。
不恢复暂停的旧自动修复流程；后续实现必须按本规格中的差距与反例重新分解。

## 2. 输入与身份

- 仅使用审核 Adapter 接纳的冻结输入；保留 case/dataset/snapshot、masking、测试选择器、源码角色与哈希。
- 原始断言、异常期待、交互与状态观察保留精确位置和稳定 ID。候选调用根须标为候选，不冒充原测试要求。
- 明确测试入口、MUT 绑定及来源：自动恢复、任务提供或诊断覆盖。诊断覆盖不能计为自动能力。
- 替换边界来自授权任务与可见依据；未知外部调用不自动等于允许 Mock 的位置。
- 无法唯一绑定时保留候选与歧义，不能按变量名、案例 ID、同名方法数量或猜测类型决定目标。
- 保留源文件、依赖、方法展开、图节点、路径深度、候选数量、时间与内存的实际限制及使用量。
  沿用现有已记录预算作为首次对照起点；任何调整单列，不因失败静默扩容。

## 3. 输出逻辑契约

下面规定字段语义，而非宣称当前序列化已支持它们。复用现有身份、源码引用、观察及成本字段；
新增内容须通过独立版本的研究封装或显式版本迁移实现，不向严格的现有 v1 对象静默加字段。

| 字段 | 必需内容 |
| --- | --- |
| identity | 冻结任务身份、masking、实现版本与后端配置 |
| analysis_boundary | 入口、可见源码及库边界、替换边界、摘要假设、预算 |
| observations | 全部原观察 ID、位置、表达式、种类与测试要求；候选根单列身份 |
| evidence | 唯一 ID、源码 ID/哈希/范围、后端事实或规则、获取方式、适用范围 |
| common_constraints | 条件/行为要求、适用观察与路径域、跨路径依据、证据状态 |
| branches | 按第4节记录的候选执行解释和条件化规格，包括尚不可消费的候选 |
| exclusions | 被排除的路径/关系、反例或规则依据；不能删除后假装从未产生 |
| coverage | 探索域、已探索候选、未展开边界、截断、完整性是否未知 |
| execution | 驱动完成/失败与错误阶段；不替代解释和证据状态 |
| cost | 输入准备、前端、图/数据库、依赖分析、组织/投影及总墙钟；不可测阶段写明 |
| review | 审查版本、对象、判据、结论、未审范围；不能由格式校验自动生成语义通过 |

共同约束可以为空，但须解释“未建立跨路径依据”，不能将空集解释为依赖行为任意。
已探索分支共有的要求可保存为探索范围内的观察结论，不能直接升级为全局共同约束。
没有全部路径的可靠分母时，coverage 不输出“路径覆盖率”。

共同约束的依据类别限定为：原测试对所有目标实现均明确要求的行为；授权接口约定中适用于全部声明情形的要求；
在有闭合依据的有限路径域中逐分支核验；或经审查的结构必要性规则及其前提见证。
结构规则须同时说明执行必要性、值/效果关联及覆盖边界，单纯支配关系不证明某个具体响应必需。
每条记录保存依据类别、适用域和前提；未闭合的枚举或未经核验的必要性推断只能留作候选。

## 4. 单个分支的完整解释

每个分支至少包含：

1. branch_id、覆盖的 observation_ids 和源级入口上下文。
2. 相关执行步骤及顺序/控制边：调用位置、实际目标、参数映射、返回或异常续接、相关定义/使用。
3. 条件：原表达式与位置、所需真假方向、值版本/绑定、适用步骤或分支、解析状态。
4. dependency_requirements：依赖调用身份、参数要求、返回形状/字段/异常/状态要求、交互顺序及各自证据。
5. external_summaries：摘要边界、保留的原表达式、输入/输出用途、未建模效果和假设。
6. 每项条件、dependency requirement 和交互要求具有独立 claim_id、support、realization、evidence_ids、assumption_ids、unknown_ids；未知必须指出影响哪些约束和观察。共同约束使用同一声明结构。
7. 解释完整性、成立依据、实现可用性三个独立状态。

“完整”指相关执行过程在边界内连贯，不是列完源码行。每个目标相关的跨过程跳转要有调用位置和续接依据；
外部步骤允许摘要，但不可悄悄当作无效果。解释断裂的部分仍交付，状态为 partial，不能冒充完整分支。
循环、递归、异步和动态派发的展开或摘要界限必须记录；未处理的上下文不能通过拼接其他调用路径补齐。
多个观察共享状态时，应保留约束兼容性与顺序。各观察分别有解释不意味着存在同时满足整个测试的解释。
分支之间记录已知互斥、兼容或关系未知；禁止任意拼接不同分支的 Mock 行为要求。

## 5. 证据与消费状态

| 维度 | 状态 | 判定含义 |
| --- | --- | --- |
| explanation | complete / partial | 是否连贯解释目标相关过程；外部摘要未知不等于结构断裂 |
| support | supported / conditional / unresolved / refuted | 有明确范围的依据 / 依赖尚未确立的假设 / 关键依据缺失 / 已被证据否定 |
| realization | grounded / conditional_only / blocked | 有依据落实行为要求 / 只有条件式要求而具体满足方式未知 / 关键矛盾或缺口阻止消费 |

这些是研究接口的状态语义，不是对历史 relation modality 或 semantic_validation 的机械重命名。
具体约束先分级，再聚合分支；禁止用多数高等级约束抵消一个关键未知。
可供消费者选用的分支须解释完整、关键结论有支持且无阻塞性未知；附条件的规格可交付但不能标为可直接实现。
supported 不表示数学证明或运行可行性已验证，必须指明其程序规则、外部约定、适用范围和审查依据。

证据升级必须增加或修正可核验依据：源码绑定、相应分析规则和见证、授权接口约定或独立核验。
代码引用存在、图上可达、LLM 自信、没有反例、后端完成和测试通过均不能单独升级语义等级。
引用/格式校验只认证引用身份；程序关系必须验证对应的规则前提。人工核验用于验收，不作为案例专用运行答案。

状态变化须保留旧状态、规则、证据和适用范围：补齐结构断点才能将 partial 改为 complete；
核验原假设或补充关键证据后才可将 conditional/unresolved 改为 supported；
有依据说明如何满足具体行为要求且关键未知已解除后，才可将 conditional_only/blocked 改为 grounded。
新增反例可将结论改为 refuted，并撤回依赖它的上层声明；新边界或截断也可使原声明降级。
上述操作不联动提升其他维度，也不把 refuted 分支删除。具体机器 Schema/校验器属于后续实现任务，当前仅交付其语义与验收规则。

例：`data = dependency.fetch(); if external_validate(data): return SUCCESS`。
可记录条件 `external_validate(data) == True`、fetch 返回值的用途和完整的条件式解释；
若可接受的 data 未知，则 realization=conditional_only，并标注阻塞具体实现的未知。
“data 应为 JSON”若仅来自 LLM 猜测，不能进入已确认返回值约束。

## 6. 必须满足的不变量

- R1：原观察身份不丢失、不替换；重复/未支持种子逐观察留证，不能借用别的断言。
- R2：调用目标和实参/形参/返回映射具有上下文依据；图上任意混合路径不构成跨过程依赖证明。
- R3：定义与使用处理覆盖；自赋值、取反、恢复旧值或条件赋值不能误判为确定切断依赖。
- R4：相关条件保留真假方向、短路结构及适用分支；不能把互斥条件全部合取。
- R5：源位置先后本身不证明执行顺序；确定在观察后发生的效果不能影响先前观察，循环/回调上下文须分别处理。
- R6：状态要求需要字段、对象/别名和效果依据；未知调用不等于无影响，也不等于一定写入具体值。
- R7：正常返回、抛出、捕获、重抛分别处理；被捕获的异常不自动逃逸，构造异常的调用仍可能有未知效果。
- R8：原表达式可保留，未知不能伪装为合法替代、自由变量或已确认的具体响应。
- R9：共同约束必须有声明路径域内的成立依据；已发现集合的交集不足以证明全局性。
- R10：截断、摘要、不可见代码及预算耗尽不等于不存在影响；失败不得擦除已保留的其他观察。
- R11：存在多个解释可正常交付；不得为产生唯一结果强制选中一条候选。
- R12：运行状态、结构完整性、证据质量、覆盖完整性和实现可用性分开报告。

## 7. 验收与运行规程

1. 先用验收清单建立逐观察预期：应恢复、应排除、应保留未知及证据来源；评阅记录不得输入分析算法。
2. 新机制先通过对应真实案例和有区分力的合成反例。每项结论记录支持/遗漏/错误/未知，不能只数关系。
3. 未证明的能力继续列为缺口；使用 case-specific 入口仅作诊断，不能替代自动入口验收。
4. 小范围语义验收通过后，冻结数据、代码、工具、预算和判据，再完整尝试165例，逐例保存结果。
5. 运行期间不改分析器、不重新定义成功。普通失败和不支持继续计入分母；若证据完整性或安全边界失效，记录中断。
   若发现语义反例，标记该版本结论无效并隔离错误声明；不能将剩余计数当作正确率。是否中止须说明结果为何已不可解释。
6. 全量之后统一归因和决定下一版本；保留旧版本及成本，不把中途修复后的结果拼成一次固定版本实验。

完成标准：能以可复核的分支记录和证据状态交付验收案例要求，排除已知错误，保留未支持范围；
完整165结果报告实际覆盖、失败类型与成本，并与历史r3及接入基线逐例比较。
不承诺165例全部成功；没有完整真值集合时不报告整体 precision/recall，已审范围与未审范围必须区分。

## 8. 实施顺序与停止条件

先落实结果状态与分支记录的校验，再对照差距表验证关键依赖机制，随后实现条件/交互的分支组织及证据聚合。
不得仅靠输出包装掩盖机制缺失；不得为完成包装而重写通用堆、异常或符号执行引擎。
每次修改须有失败根因、适用范围、正反例和实际成本；工具选择由这些证据决定。
若成熟能力与当前输入不匹配，交付具体边界和对照证据，再单独决定替换或扩大范围。
本规格及配套文档完成，不代表代码实现或实验完成；现有暂停任务不能直接续跑来替代重新规划。
