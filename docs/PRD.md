## 1. 背景与目标

同一测试断言可能被多种Mock满足，其中部分Mock绕开了测试本来要覆盖的场景。例如，测试希望覆盖缓存未命中后的查询与回填，但Mock直接返回缓存结果，最终返回值断言仍然通过。

本项目在生成Mock前增加分阶段场景推断与静态退化对照，使生成器明确：当前要覆盖什么场景、依赖应提供什么行为、哪些关键行为需要发生和被观察。发现实质证据缺口后可在同一共享预算内补查、重构并再次对照。

研究目标是：**在相同可见信息与总预算下，降低“原测试通过但目标场景未被有效测试”的比例，并保持合理的生成成功率和合法替代接受能力。** 首版允许推断误判，通过独立评价测量收益与代价。

### 1.1 工作定义

| 概念 | 本项目定义 |
|---|---|
| Mock代码 | 测试中对象创建/替换、依赖行为配置（stubbing）及Mock交互验证（verification）；具体修改位置由任务已有区域/槽位约定决定 |
| 原目标 | 可见测试已明确的输入条件、普通输出/异常/状态断言及明确交互预期；隐藏verification槽位的存在本身不提供具体预期 |
| 场景 | 当前测试拟覆盖的一组前提、依赖响应及关键行为；可有多个合理候选 |
| 合理场景 | 与当前任务相符，依赖行为有上下文支持，关键行为可以发生并被观察 |
| 退化替代 | 一种可能满足原断言、却绕开有依据的场景行为的Mock方案 |
| 场景绕过 | 原测试通过，但有依据的关键场景行为没有发生 |
| 观察缺口 | 关键行为发生，但相关错误不能被生成测试的断言或获准检查区分 |
| 合法替代 | 同一场景内，值、构造方式或实现形式不同，但仍满足有依据的行为关系的Mock |
| 退化对照 | 在推断中提出并比较主场景与退化替代；首版是静态分析，不宣称已运行 |

“场景绕过”和“观察缺口”分别记录，可以同时成立。不同Mock写法本身不构成退化。

本文“原断言保持”指保留任务固定的可见普通oracle及既定预期；在授权Mock验证区域生成`verify(...)`、`assert_called_*`等，属于Mock代码生成，不是修改普通oracle。普通setup、目标调用和被测实现同样保持不变。

## 2. 使用者与任务

| 使用者 | 需要完成的任务 | 获得的结果 |
|---|---|---|
| 研究者 | 查看Agent为何选择某个场景、是否绕开关键行为 | 场景卡、来源、退化对照、未决项 |
| Agent开发者 | 实现可控且可审计的推断流程 | 输入输出约定、阶段规则、预算及验收用例 |
| Mock生成器 | 将场景要求实现为具体代码 | 依赖行为关系、关键行为、允许变化、检查建议 |
| 实验评阅者 | 比较有无场景推断及退化对照的效果 | 冻结的评价标准、逐次产物和汇总指标 |

首版使用现有任务入口及文件报告，不新增网页界面。使用者提交一个获准任务，运行后查看主场景、依赖约束、退化风险与终止原因。

## 3. 首版范围与交付顺序

| 阶段 | 必须交付 | 完成标志 |
|---|---|---|
| M1：推断原型（P0） | 单Agent分阶段流程、现有工具接入、场景契约、研究记录、预算控制 | 第10节P0验收通过，可独立检查推断产物 |
| M2：生成接入（P1） | 外部生成器消费契约、编辑范围检查、运行结果绑定 | 场景卡可落实到授权修改区域，检查建议去向明确 |
| M3：可行性实验（P1） | A/B/C对照、10例试验及逐次评价 | 按第11节交付全部计划运行与失败记录；效果如实报告 |

M1先以Python任务完成端到端接入；现有Java能力保留，Java不是首轮10例试验的前置要求。运行模型沿用项目配置，不在PRD中绑定供应商或特定型号。

首版范围外：自由读取全仓新文件、真实依赖在线采样、完整形式规格合成、通用求解器接入、多Agent协商、自动改写被测实现。已有受限源码绑定研究可以以后接入。

现有生产V0.1/V0.2及正式Schema保持兼容，新策略进入独立研究入口。M1仍只输出约束；代码生成和测试执行属于外部研究链。当前边界以[架构导读](architecture.md#研究路径)和[研究交付决策](adr/0001-research-spec-delivery.md)为准；历史外部仓库核对记录的名称保留在文末。

## 4. 总体流程

```mermaid
flowchart LR
    A[审核并冻结的任务材料] --> B[提取原目标与候选场景]
    B --> C[围绕疑问查询现有工具]
    C --> D[形成条件式依赖规格]
    D --> E[检查过弱、过强及证据缺口]
    E -->|实质缺口| C
    E -->|证据足够或受限停止| F[自包含依赖规格与审计记录]
    F --> G[外部Mock生成器]
    G --> H[独立执行与评价]
```

独立评价材料只进入H，不进入推断或生成上下文。M1的输出可以独立使用，无需等待M2/M3。

### 4.1 推断阶段规则

| 阶段 | 必须完成 | 退出条件 |
|---|---|---|
| 目标提取 | 提取原输入、断言、固定条件及替换边界；记录证据位置；形成可修订的初始候选或重要问题 | 原始目标已定位；初始候选为空或材料不足仍进入查询及部分规格构造 |
| 定向查询 | 每次声明一个可能影响原目标或最终约束的问题；记录返回事实及影响，并可新增、替换或放弃候选 | 信息足够、材料不可获得或共享预算耗尽 |
| 场景构造 | 按任务证据、依赖语义与显式假设形成条件式规格；保留有据的单一分支、合法替代或实质歧义 | 得到可交付规格，或保留冲突/未决及其影响 |
| 退化对照 | 从过弱和过强两个方向检查约束；提出有依据的替代、反例、观察不足或补查需要 | 没有实质缺口，或补查结果已重新构造 |
| 交付 | 校验并输出自包含规格、正式契约、选择结果、依据、未决项、费用与终止原因 | 输出有效，或结构错误无法修复 |

允许初始材料充分时零查询，也允许在访问或预算受限时交付明确受限的部分结果。
完整方案仍须记录对照尝试；不能为了凑步骤虚构替代。CONSTRUCT 或 CONTRAST 发现可能
实质改变规格的证据缺口时，可在同一运行与共享预算内返回 QUERY，再更新候选和规格。
这种语义补查与只修复格式的模型调用分别记录。原始目标在循环中保持不变，不能随候选收缩。

## 5. 输入约定与预算

### 5.1 任务输入

复用`UnifiedTask`，保持原字段含义：

- 任务身份、语言、被测源码与遮蔽测试。
- 允许接口及其解析状态。
- 已审核补充材料、source_id及原文件行号。
- 执行上下文元数据和输入可见性策略。

宿主必须生成本次输入快照标识与哈希，冻结原输入和原断言。初始 payload 只包含已审核的
可见片段；显式仓库模式还可在同一审核冻结仓库及访问策略内发现、读取和登记新增来源。
“未出现在初始材料中”不等于“不可探索”，工具也不能越过宿主绑定的准入范围。

运行配置与任务语义分开保存，至少包含策略版本、模型配置、实验组、工具预算、总token/时间预算，以及M2使用的任务授权Mock区域及其身份。批量运行必须在开始前明确预算值，所有组一致；实际使用量一并记录。

### 5.2 默认预算

| 项目 | 默认限制 | 计数规则 |
|---|---|---|
| 保留的正式候选 | 由相关证据和共享预算约束 | 语义不同；是可随证据更新的工作假设，历史被替换候选只留修订记录 |
| 只读工具查询 | 片段回放最多6次；仓库模式由共享资源门禁停止 | 片段回放中失败调用和重试均计入同一额度；仓库模式不设置固定查询次数，仍受总 Token、费用、超时和重复无进展保护 |
| 退化对照 | 由变体和共享预算约束 | C 变体在每次完成构造后检查过弱、过强和观察不足；补查后可再次构造及对照，不通过更名重置预算 |
| 场景卡修订 | 由共享预算约束 | 对照后可补查并重新构造；不得通过更名重置预算或抹去修订历史 |
| 最终输出格式修复 | 最多1次 | 仅修结构/引用格式，不改变场景语义；计入总模型预算 |

控制器必须终止超额动作。格式修复不是新增推断轮次；网络或模型错误的重试必须有界并计费。总预算不足时保留已有可校验内容和未完成原因，不以删除关键要求获取成功状态。

M2接入后，总模型预算覆盖推断、生成及修复。M1阶段推断预算作为其中的显式子预算记录，不向B/C组额外赠送推断额度。

## 6. 功能需求

| ID | 优先级 | 必须实现的行为 |
|---|---|---|
| FR-01 | P0 | 固定任务身份和原目标；不能改写原输入、固定普通oracle或既定测试预期；授权Mock验证区域中的待生成verification不属于被禁止的普通oracle修改 |
| FR-02 | P0 | 提出与原目标相关的当前候选；每个候选包含条件、依赖行为、依据和未决问题；新证据可使其新增、替换或放弃；值的语法差异不算不同场景 |
| FR-03 | P0 | 工具查询绑定影响原目标或最终约束的待解问题；返回后记录支持、削弱或无新增信息；越界source_id由宿主拒绝 |
| FR-04 | P0 | 优先选择有明确任务依据、附加假设较少的候选；不得以更容易PASS作为选择理由；仅测试名或实现调用不足以强制某交互 |
| FR-05 | P0 | 依赖约束采用“条件→允许响应/异常及状态影响”；标明目标调用、参数关系和来源；无依据的具体值仅作实例，证据要求的精确值必须保留 |
| FR-06 | P0 | 每次构造最多突出3项最关键行为，可以是输出、异常、调用或状态变化；完整规格仍须覆盖所有影响原目标的依赖要求，不得把所有调用自动变成必须verify |
| FR-07 | P0 | 静态检查约束过弱、过强和观察不足，记录替代、绕过行为、任务依据和区分观察；重要证据缺口回到查询，没有运行证据时标为未验证 |
| FR-08 | P0 | 输出同场景合法变化和未决项；无法支持的精确常量、次数、顺序不得自动成为硬要求 |
| FR-09 | P0 | 复用正式ScenarioContract；新增研究信息独立保存；宿主验证结构、身份、引用、原文与预算，不宣称完成语义证明 |
| FR-10 | P0 | 记录完整阶段结果、工具回执、修订前后差异、模型与用量、终止原因；语义不确定与运行错误分开 |
| FR-11 | P1 | 生成器按冻结场景和任务授权Mock区域生成setup、stubbing及verification；对编译、拼写和matcher错误修Mock；场景变更请求独立记录 |
| FR-12 | P1 | 评价材料预先冻结并与生成隔离；执行A/B/C对照，保留失败/超时/未决及各指标分母 |

证据基础分为测试要求、当前 MUT 的实现事实、依赖约定、场景推断和附加假设。
冻结 MUT 执行链是本轮的回归分析参考，用于理解路径和依赖使用，不是已经验证正确的业务规范。
测试、实现和依赖依据冲突时保留冲突及其对规格的影响，不能用不合理 Mock 响应强行消除。
主场景允许包含有据推断，仍标为候选；明确引用只说明出处可追溯，不使推断自动变成已证实事实。

## 7. 输出规格

每次运行保存以下四个逻辑产物；文件名按研究入口约定，字段含义保持一致。

| 产物 | 内容 | 必需性 |
|---|---|---|
| `scenario_contract.json` | 兼容现有`mock-spec.scenario/v0.1`的契约 | 能形成有效契约时输出；不得用空壳充当成功 |
| `dependency_spec.json` | 版本化、自包含的生成器消费规格；绑定审核 task、正式契约、范围、依据、允许变化、未知、冲突、停止摘要及运行身份 | 形成可校验的完整或部分规格时输出；消费者无需读取完整推理轨迹 |
| `inference_record.json` | 选择依据、查询、退化对照、允许变化和修订记录 | 必须；失败时保存已完成部分 |
| `run_manifest.json` | 身份、版本、输入/产物哈希、配置、状态、预算和错误 | 必须，包括失败运行 |

首轮语义校准的研究草案见 [Scenario Contract](scenario-inference.md#首轮-spec-语义校准研究草案)。
评阅区分条件内义务、依据充分度、允许变化、未知及关键需求覆盖；正式契约的 Claim 状态保持不变。
生成器消费 `dependency_spec.json`，其中已经封装理解规格所需的 task、正式契约及研究语义；
`inference_record.json` 继续用于审计。只读取 statement、查询停止理由或完整轨迹中的零散字段都不满足消费约定。
有证据支持且满足原目标、依赖约定和适用条件的多个分支是允许选择；仍无法确定是否合法的分支是
实质歧义。两者不能都用旧 `AMBIGUOUS` 状态解释，也不得因为未发现反证就扩大允许集合。

### 7.1 正式契约映射

| 内容 | 现有字段 | 使用要求 |
|---|---|---|
| 原目标 | `test_objectives` | 忠实记录原测试已表达的要求；新推断的Mock检查建议进入`verification_candidates`，不冒充原要求 |
| 候选场景 | `scenario_hypotheses` | 保存与当前目标相关且有据或明确标为未知的条件分支；选择、合法替代和未决状态另存研究语义 |
| 依赖行为关系 | `dependency_constraints` | 必须绑定场景条件与证据；首版使用结构化文字 |
| 关键交互 | `expected_interactions` | 仅关键行为中的交互项；保留`assertion_policy=not_implied` |
| 检查建议 | `verification_candidates` | 描述观察及其依据；在任务授权Mock验证区域落实，无法落实时记录原因，不扩大修改范围 |
| 来源 | `evidence` | source_id、原行号、原文和解释可核对 |
| 未决项 | `uncertainty` | 写清影响哪个决定及缺少什么 |

不改变现有`required/candidate/unknown`含义；`required`只表达声明条件和场景内的要求。新增的选择状态不覆盖Claim状态。

### 7.2 研究记录最小字段

| 字段 | 内容 |
|---|---|
| `schema_version` | 当前研究记录版本 `scenario-inference-record/v0.4`；历史运行按各自产物中的版本解释 |
| `run_id, case_id, input_hash` | 与运行清单及输入快照一致 |
| `result_status` | SELECTED / ALTERNATIVES / AMBIGUOUS / INCONCLUSIVE / ERROR |
| `selected_scenario_id` | 仅SELECTED时必填，其余为null |
| `selection_rationale` | 选择或不选择的原因，关联证据与候选 |
| `claim_basis` | 相关命题的任务要求/实现事实/场景推断分类及引用 |
| `query_log` | 轮次、问题、候选、工具参数、返回引用、影响 |
| `critical_behaviors` | 行为描述、场景id、目标/证据关联、观察方式；每次构造最多突出3项，不替代完整依赖约束 |
| `allowed_variations` | 可变值/构造/次数等；若无已知变化可列，显式说明未识别，不推断唯一 |
| `degeneracy_contrast` | 状态、替代Mock方案、绕过行为、依据、预期区分观察；执行状态固定为not_executed |
| `revision_log` | 修改对象、前后内容、证据原因；未修订为空数组 |
| `unresolved` | 未决问题、影响与所需信息 |

每条依赖关系必须能读出目标接口或调用位置、适用条件、参数关联、允许返回/异常，以及相关状态影响；无关的状态字段可写不涉及。符号无法解析且影响实现时标为关键未决，不能编造具体调用绑定。

`degeneracy_contrast.status`取`proposed`、`none_identified`、`unavailable`或`disabled_by_variant`：分别表示提出候选、完成尝试但未找到、因证据/预算未完成、B组按消融关闭。所有静态结论都不写成实测通过。外部执行证据另存，并绑定契约与代码哈希。

### 7.3 结果与失败语义

| 状态 | 必须满足 | 下游行为 |
|---|---|---|
| SELECTED | 有有效契约，主场景可识别，无阻止当前生成的关键未决；可有非关键未知 | 允许生成器消费；不等于语义正确或测试已通过 |
| ALTERNATIVES | 多个完整分支各自有正向证据和前提，且没有阻塞未知 | 生成器可选择其中一个完整分支，不得合取分支或只取局部约束 |
| AMBIGUOUS | 一个或多个分支是否符合当前任务仍未确定，或缺少必要的选择依据 | 不自动挑更容易通过者；保存未决依据，本次默认不生成 |
| INCONCLUSIVE | 无法形成可用选择，如关键绑定缺失、材料或预算不足 | 完整校验的 partial/conflict 规格可交付限制说明；未完成规格仅留审计诊断 |
| ERROR | 输入不合法、运行失败或最终结构校验失败 | 不下发契约，记录错误阶段 |

`stop_reason`另行记录正常完成、预算耗尽、证据耗尽、工具/模型错误或输出无效。额度用尽仍能提交有效选择时可为SELECTED，但必须保留预算终止标记；结论不充分时不能伪装SELECTED。

多个分支只有在各自条件、依赖语义和目标覆盖均有依据时，才是同一条件式规格中的合法替代。
生成器可以选择其中一条完整分支具体化，并遵守该分支的全部约束。相同最终返回值、没有找到反例，
或更容易生成，都不能把未决分支提升为合法替代。同一关系允许多个具体值则属于允许变化，不构成场景歧义。

## 8. 下游生成与修改规则

M2统一沿用任务已有的Mock代码编辑区域，A/B/C使用同一授权范围。生成内容包括：

| Mock代码部分 | 允许生成的内容 | 约束 |
|---|---|---|
| 创建与替换 | Mock对象、patch/spy及相关装配 | 仅在任务授权的Mock setup区域 |
| 行为配置 | 返回值、异常、side effect、必要的状态与响应序列 | 符合所选场景，保留合法值和实现形式 |
| 交互验证 | 调用参数、必要调用、以及有依据的次数/顺序验证 | 在任务已有VERIFY区域或verify槽位内；与场景和证据关联 |

现有Java输入有`MOCK-STUB`与`VERIFY`双区域，审核的Python案例有`mock_stub_*`与`verify_*`槽位。区域是落地位置，具体要求由推断产生；不要求恢复隐藏参考代码原样，也不因槽位存在就强制某个调用验证。

若某任务缺少一项观察所需的授权位置，记录该项未落实及原因，不另增通用测试增强模式、不越区改普通oracle。外部诊断可补充评价，但只有实际进入交付Mock验证并执行的检查才计入生成测试自身能力。

宿主必须检查生成前后原输入/断言和允许区域。越界修改作为不合规产出，不计成功。生成结果绑定所消费契约的哈希，后续修改代码后旧反馈标为过期。

场景冻结后，生成器可因新适用证据或编辑范围无法实现而提交变更请求。首版将请求落盘并结束本次，不隐式重启推断；另起一次运行时分配新run_id并关联原记录。仅编译、拼写、matcher错误在当前生成预算内修复Mock。

## 9. 示例：缓存未命中后的查询与回填

以下为验收用人工示例，不代表已运行结果。任务说明明确要求缓存未命中时查询并回填；被测代码支持该路径；原断言为返回用户id=7。

| 输出项 | 预期内容 |
|---|---|
| 主场景 | 缓存未命中后查询并回填 |
| 依赖响应 | `cache.get(7)`返回缺失；`repo.fetch(7)`返回id为7的用户；写入正常完成 |
| 关键行为 | 仓库接到正确id；查询结果写回对应缓存键 |
| 退化替代 | 缓存直接返回用户，可能使原断言通过但跳过查询与回填；标为未执行 |
| 区分观察 | 查询是否发生、回填键值是否正确；无需强制所有调用的精确次数 |
| 合法替代 | 保持用户id及相关关系，改变无关字段或对象构造方式 |

若去掉明确任务说明，只剩返回值断言，系统可将“命中”和“未命中”保留为候选，不能仅凭当前实现包含回填分支就强制回填。是否仍能选择由剩余适用证据决定。

## 10. 功能验收标准

验收以人工构造的固定输入/模型输出回放检查控制器，以小规模真实模型运行检查产物可读性。要求流程正确，不要求LLM在所有案例上语义判断正确。

| ID | 对应需求 | 验收场景与预期结果 |
|---|---|---|
| AC-01 | FR-01、09 | 修改原断言或伪造任务身份：宿主拒绝不匹配产物；原输入快照保持不变 |
| AC-02 | FR-02、04 | 两个候选证据无法区分：输出AMBIGUOUS、无主场景id，保留两者依据；不自动调用生成器 |
| AC-03 | FR-03、10 | 片段回放请求第7次工具查询：宿主阻止，前6次和拒绝原因可见；仓库模式改由共享资源及重复无进展保护停止，不套用固定六次限制 |
| AC-04 | FR-03、09 | 查询未知source_id或引用不存在行：拒绝/校验失败，不能产生“已证实”结论 |
| AC-05 | FR-05、08 | 用户对象存在无关字段变化：契约允许关系不固定完整字面量；精确次数要求有依据才能保留 |
| AC-06 | FR-06、07 | 缓存示例：对照能表达“正确返回但绕过回源回填”的区别；检查建议绑定任务依据 |
| AC-07 | FR-07、10 | 对照未经执行或未找到：分别记录proposed/not_executed或none_identified，不写已通过/已发现缺陷 |
| AC-08 | FR-09、10 | 修订或对照发现实质缺口时沿同一预算补查并重新构造；总预算耗尽时停止，保存已验证的部分规格检查点或诊断、计数与终止原因，不无限重试 |
| AC-09 | FR-11 | 在授权VERIFY/verify槽位中生成有依据的Mock验证：合规；越出授权区域、改普通oracle或被测实现：拒绝；外部诊断另列 |
| AC-10 | FR-11 | 生成器仅因编译错误请求更换场景：保持场景，要求修Mock；合法场景变更请求单独落盘 |
| AC-11 | FR-10、12 | 批量中出现失败、超时、未决：每次都有manifest，汇总能核对计划数与各状态数 |
| AC-12 | FR-12 | 生成任务尝试读取评价用故障、合法替代或隐藏参考：输入包/工具层不可见；评价只在生成结束后读取 |

AC-06属于固定示例的预期语义检查，可在回放中验收结构逻辑，在真实模型运行中记录通过/失败；不得据单例通过宣称普遍防退化。

## 11. 实验与效果验收

### 11.1 首轮配置

采用10个已获准的Python案例：4个目标明确且容易绕过、4个存在多个合法Mock、2个关键意图证据不足。分层标签以人工预审为准，每例指定一个主类别。开发调参案例与正式10例分离。保留筛选过程，这批目的性样本用于可行性判断。

| 条件 | 运行方式 |
|---|---|
| A | 直接生成Mock；拥有相同可见材料、只读工具及外部执行额度 |
| B | 场景推断→生成；关闭退化对照，其余接口与C一致 |
| C | 完整场景推断→退化对照→生成 |

每例每条件3次，计划90次试验。出现ALTERNATIVES/AMBIGUOUS/INCONCLUSIVE/ERROR仍计为一次试验，不要求一定生成代码。固定模型、运行配置、输入、任务授权Mock区域、整条流程预算和最终候选选择规则；记录实际费用，禁止事后从同次轨迹挑最好的代码替换最终产物。

两位评阅者在正式生成前冻结：允许场景及证据、关键行为判据、相关故障变体、同场景合法替代及其适用条件。判据允许多个场景；分歧无法裁决的条目标为不可判定。评阅者的产物与生成可见输入隔离，不能根据某组输出反向编标准。

首轮每个可进行故障评价的案例只冻结1个主要故障，统计单位为“一次计划试验”，不是“试验×故障”。主要故障必须对该案例认可的场景及合法Mock替代共同适用；无法满足时，在生成前将该案例标为故障指标不适用，仍保留其他评价。这样即使某次无产出，其是否进入故障分母也已确定。额外故障可作补充分析，不混入主指标。

### 11.2 指标与分母

| 指标 | 统计定义 |
|---|---|
| 原断言通过率 | 合规产出在未改被测实现上满足原测试输入与固定普通oracle的次数/计划试验数；生成Mock中的交互验证结果另列 |
| 完整测试通过率 | 固定测试与生成Mock组成的完整测试全部通过次数/计划试验数，包含Mock verification |
| 场景绕过率 | 原断言通过且有独立判据的产出中，关键场景未发生的比例 |
| 观察缺口率 | 在原实现上完整通过、有预置主要故障且故障运行可判定的产出中，生成测试未能因该故障失败的比例；基准已失败、无适用故障和环境错误不进入此项分母，数量另列 |
| 主要故障检出率 | 在原实现上完整通过、在预置主要故障上因该故障失败的次数/具有预先适用主要故障的计划试验数；无产出、基准失败、环境错误均不计检出且保留在分母，分别报告原因 |
| 合法替代误拒绝率 | 基准完整通过，保持待评价Mock verification，替换为同场景合法Mock行为配置后被错误拒绝的次数/成功完成替代测试的适用次数 |
| 未决与失败分布 | SELECTED/ALTERNATIVES/AMBIGUOUS/INCONCLUSIVE/ERROR、超时、越界等逐项计数；附实际token、耗时和成本 |

在场景与故障观察两项都可判定的共同集合上，报告场景绕过与观察缺口的并集及重叠数，作为总体退化描述；其他产出保留各自状态，不推测并集。普通oracle通过但生成Mock的交互验证在原实现上失败的产出单列并归因，不能把其在故障版本上的既有失败算作检出。所有比率给出分子、分母和未执行/不适用/不可判定数量。外部场景检查检出的错误独立统计，不计入生成测试自身故障检出。

运行结果必须区分“确实测得原断言通过”和“未测”。若Mock交互验证提前中断而无法判定普通oracle结果，不推测其本会通过；需要普通oracle专用重放时由外部评估器执行并单独记录，其结果不替代完整测试结果。

### 11.3 继续与简化决策

首轮不预设效果提升百分点，不以全部任务都能推断作为开发验收条件。交付逐例A/B/C比较、误判原因和成本：

- C相对B减少退化且代价可接受：继续扩大样本。
- B与C接近：优先保留较简单的场景推断。
- 合法替代误拒绝上升：删减无依据的过强约束。
- 主要失败来自调用绑定或工具接入：优先修复工程链，再比较推断策略。

结论必须同时考虑成功产出数量，不能只通过大量弃答降低条件化退化率。
