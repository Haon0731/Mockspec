# Step 6 — Scenario Inference Agent V0.2 规格

状态：根据用户确认的 Q1–Q6 编写，待作为后续任务拆分和实现依据；不是实现或验证完成报告。

## 1. 问题与目标

V0.1 通过 OpenAI Agents SDK 对完整可见 UnifiedTask 进行一次无工具推理，生成 Scenario Contract。它不能按推导需要调用确定性的程序分析工具来定位证据、核查分支结构或修正依赖使用假设。

V0.2 在同一 SDK 上增加受预算约束的多轮推理和三个只读 Function Tools。模型自主决定是否、何时以及如何调用工具，使用结果修正候选场景，最终仍输出现有 Scenario Contract，并通过现有 Validator。

本轮研究变量是“工具增强推理”。初始源码可见范围与 V0.1 相同；不同时研究按需加载源码。工程交付与场景质量效果分别评价，不以质量必须提升作为完成条件。

实现须具有案例通用性，不按 case_id、flask_308、JarFiles、固定行号或目标方法名硬编码推理逻辑。两个案例只用于验证。工具结果显式区分 unresolved、unsupported 和分析失败。

## 2. 基线与范围

- V0.1 归档提交为 `f699554`；实施前核对当前基线身份和工作区差异。
- `src/mock_spec/inference.py` 与 `src/mock_spec/prompts/scenario_v0.1.txt` 逐字冻结；V0.1 历史实验记录不覆盖、不重写。
- 新增 `src/mock_spec/inference_v02.py` 和独立 V0.2 Prompt；允许少量重复代码，不通过修改 V0.1 核心来抽象公共逻辑。
- 宿主 CLI 提供显式版本选择，默认保持 V0.1。原有默认调用和离线回放语义保持兼容。
- 复用 OpenAI Agents SDK、UnifiedTask、Scenario Contract Schema 和 Validator，不建立第二套 Agent 框架，不扩展 Contract Schema。
- 复用 Step 5B 已验证的 Python AST 与 Java Spoon 能力，不把历史探针输出当成本次工具执行结果。

## 3. 使用场景

1. 研究者可按原方式调用 V0.1，获得可复现的无工具基线。
2. 研究者可显式选择 V0.2，在相同可见输入下观察模型自主取证。
3. Agent 可查找指定可见源码片段及原始位置，为 Contract 提供精确引用。
4. Agent 可获取调用、条件、分支、返回及异常处理的语法结构，核查候选场景。
5. Agent 可查询依赖调用和可靠的局部使用关系，区分已提取事实与未解析关系。
6. Agent 在工具失败后仍可依靠已有证据完成推导，并如实表达不确定性。
7. 研究者可审计成功与失败运行的模型响应、实际工具调用、验证状态和成本。
8. 研究者可比较两个版本的质量收益、退化和成本差异，而不把合法引用误当成语义正确的证明。

## 4. 输入与信任边界

宿主通过现有审核 Adapter 加载冻结案例，构造 UnifiedTask。V0.1 和 V0.2 初始接收相同的完整可见任务，包括 MUT、Masked Test、允许接口及支持源码。

工具以当前任务的内存 SourceStore 为访问边界，只允许 source_id 和受限查询参数；不得提供任意路径、命令、任意查询代码或扩大访问范围的参数。非法 source_id、越界行号和不可见符号返回明确错误或 unresolved，不回退到物理源码仓库。

工具不得读取原始未遮蔽测试、Ground Truth、Reference Mock、历史生成模板、私有语义信息、依赖目录或额外源码。解析器只分析当前任务已经可见的文本，不运行被分析程序。若 Spoon 需要临时输入，临时内容仅来自这些文本，临时位置由宿主控制，不构成模型的文件访问能力。

原 Case ID、masking 和原文件行号保持不变。不同 source_id 即使来自同一文件，也不得跨越各自允许范围。源码、注释和工具返回的源码片段均是数据，不构成授权指令。

## 5. 三个工具的行为契约

工具的具体参数名和内部类型可在实现时确定；以下行为是验收约束。

| 工具 | 能力 | 结果及边界 |
| --- | --- | --- |
| `inspect_source` | 按 source_id 和有界位置准确取得可见源码 | 返回 source_id、原文件行号和原文；保留缩进；不补读切片外内容 |
| `inspect_program_structure` | 提取调用、条件、分支、返回及异常处理结构 | 标明分析后端和语法事实类别，返回对应源码位置；词法包含和分支极性不等于控制流或路径可行性证明 |
| `inspect_dependency_usage` | 提取依赖调用及可靠的局部使用关系 | 区分语法嵌套、局部声明引用和未解析关系；不得把名称相同或邻近语句升级成已证明的数据流 |

共同要求：

- 结果包含明确状态、证据位置、能力限制及必要诊断；区分成功、部分结果、未解析和错误。
- 截断或部分解析须显式标为 incomplete，不能把空结果解释为“无调用或依赖”。
- Python AST 保留函数切片的原始行号；Java Spoon 不把外部声明或不可见实现当成可用证据。
- 只有返回/抛出/捕获等语法结构时，不声称证明异常传播、跨语句 def-use、跨过程数据流或路径可满足性。
- 对工具结果大小、分析时间和调用数量设置有界限制；解析器错误诊断不得泄露宿主秘密或无关文件内容。
- 工具分析的是可见程序事实；如何组织场景假设及依赖行为约束仍由 Agent 完成。

## 6. V0.2 推理行为

V0.2 使用同一 SDK 的 Agent、Function Tools 和运行循环。独立 Prompt 说明工具能力、证据边界、错误处理、unknown 使用及现有 Contract 输出要求。

允许零次工具调用，不强制使用 inspect_source 或任何指定工具。工具可以帮助模型核查已有假设；不要求暴露私有思维链，留存工具交互与最终可核查结论即可。

每次运行受全局时间和轮次等限制。对 Token 与费用设置运行前估算、逐次记录和后续调用门禁；不能准确获知的用量或价格明确标记未知，不能用零代替。正在执行的远端请求可能已产生成本，不能将本地取消或事后统计宣传为严格费用硬上限。

| 情况 | 预期行为 |
| --- | --- |
| 单次工具失败 | 返回明确错误与诊断，保留记录；允许 Agent 在剩余预算内继续 |
| incomplete / unresolved | 保留不确定性，不解释为依赖不存在 |
| 工具失败后生成合法 Contract | 可以正常完成；保留失败轨迹；合法结构本身不证明无过度推断 |
| 全局时间、轮次或费用门禁触发 | 停止运行，不额外请求收尾回答；保存已获得的轨迹和用量 |
| Contract 结构或证据验证失败 | 记录失败类别，不把候选输出当成有效 Contract，不自动质量重试 |
| 正常生成且 Validator 通过 | 记录有效 Contract，并独立进行语义审查 |

## 7. 小规模实验协议

### 7.1 正式矩阵与冻结配置

仅使用 Java JarFiles 和 Python flask_308 两个已审核案例。V0.1/V0.2 各运行一次，计划共 4 次有效运行；受模型可用性、故障次数和预算门禁约束，不能保证一定获得 4 份有效 Contract。

正式实验开始前固定并记录：

- 模型 ID，可获得时记录实际解析版本；无法获得时明确未知。
- SDK 与解析器版本、代码提交、Prompt 版本及内容身份。
- 案例与冻结 snapshot 身份、序列化 UnifiedTask 身份。
- 采样设置或 SDK/provider 默认设置、版本间必要差异。
- 总超时、轮次、工具调用次数、工具输出大小、Token 限额和计费依据。
- SDK/传输层重试策略，避免未记录的隐式重试掩盖实际成本。

具体模型和数值限额属于实施配置，当前尚未确定；须在实验前记录，不能追随结果质量调整。正式比较尽量保持模型、输入和共同采样设置一致。历史 V0.1 结果只在模型版本及运行条件核对一致时才可承担正式基线，否则作为历史参照并重新运行。

### 7.2 重试和费用

- 全轮最多 2 次技术故障重试，不按案例分别分配 2 次。
- 不因为场景质量差、未调用工具或结论不符合预期而重试。
- 技术故障包括明确的连接、服务端或运行基础设施故障；结构/证据错误及质量退化记录为结果，不能伪装成传输故障重试。
- 全轮费用目标上限 US$5，失败和重试也计入。每次调用前检查剩余预算和估算，运行后更新记录；可获取的已消耗费用超过门禁时不启动后续调用。
- 单次远端请求的超额和未知计费可能无法严格阻止，报告需披露预算保证的实际范围。

### 7.3 模型不可用与诊断案例

模型调用可用时进行 live inference。不可用时只做离线工具与 SDK 集成验证，记录原因及未覆盖的验收项，不伪造模型结果或质量对照结论。

允许另设独立诊断案例，但不扩展正式数据集。其结果单独标识，不能替代两个真实案例的观察。诊断 live 请求须在运行前另列次数分配并纳入同一 US$5 预算，不能悄然增加正式实验或重试次数；本规格不把额外 live 诊断作为必做步骤。

## 8. 留证与质量比较

每次运行保存：运行模式、身份与配置、时间、原始模型响应、实际工具名和参数、工具结果及状态、调用顺序、耗时、错误类别、Token 用量、费用估算及依据、验证结果和有效 Contract（若有）。失败运行同样保存已有信息，不伪造 Contract，也不把未获知用量写成零。

明确区分：模型请求的工具调用、工具实际执行、工具成功返回、有效 Contract、语义审查结论。这些不是同一个成功条件。

质量比较使用相同可见证据，逐项记录：

重点评价场景约束准确性、完整性、证据增量和推导错误；JSON/Validator 通过率仅属于工程指标，不能代替研究质量评价。

- 证据位置与引用准确性，以及原文是否支持结论。
- 分支条件、替代路径和异常出口是否被合理表达。
- 依赖行为约束是否有证据、条件和适当的适用范围。
- 无依据的 required、调用次数或禁止额外调用等过度推断。
- 对未知、未解析和遮蔽内容的处理。
- 工具提供了哪些新增分析事实，最终 Contract 是否引用或反映这些事实；不能仅凭时间先后断言工具导致改进。
- Token、工具执行耗时、模型耗时和费用增量。

同时记录改善、无变化和退化。区分工程错误与模型推理局限；证据不足时不作确定归因。不得为获得更好结果反复调整 Prompt。若必须修复工程错误，保留原失败记录和变更身份，说明修复后结果与原配置的可比性。两个案例只支持案例级观察。

## 9. 测试与验收

优先沿用现有 SourceStore、SDK Runner 和 Contract Validator 的测试接口，以可观察行为为主，减少新增测试专用抽象。

| 验收项 | 必要证据 |
| --- | --- |
| V0.1 冻结与兼容 | 原 inference.py、Prompt 逐字一致，历史记录无修改；默认 CLI 及原有回归通过 |
| 输入隔离 | 非法 source_id、路径、越界范围被拒绝；解析输入仅包含当前任务可见文本，无隐式回退 |
| 源码定位 | Python 切片偏移和 Java 位置可与原文核对；Contract 引用通过现有 Validator |
| 程序结构与依赖事实 | 两语言覆盖调用、条件、分支、返回/异常语法和可靠局部关系；未解析与截断明确标识 |
| 多轮 SDK 集成 | 离线 SDK 运行能完成工具请求→实际工具执行→模型收到结果→Contract 验证；同时验证零调用路径 |
| 错误恢复 | 工具失败后仍可形成有效 Contract；失败记录存在，不把错误解释为无依赖 |
| 全局门禁 | 到达上限不再发起模型请求，不增加收尾调用，保存已有证据 |
| 真实自主行为 | live 轨迹实际观察到模型自主工具调用；强制调用、宿主预调用和脚本回放不算 |
| 结果可审计 | 成功、失败均有身份、轨迹、用量/费用或明确缺失说明；离线与 live 标签准确 |
| 质量报告 | 按固定维度逐案比较，退化和未验证项如实披露 |

两个真实案例都未触发工具调用时，必须写明“自主工具使用尚未验证”，不能宣称该能力已通过端到端验证。模型不可用时亦不能将离线集成通过写成真实推理已验证。

工程实现正确与场景质量提升分别判断。允许交付未改善或退化的研究结果；不能因为结果质量不足无限延长开发，也不能隐去工程或 live 验证缺口。

## 10. 非目标与停止条件

不修改 Stub-Tester，不运行旧实验，不读取 Ground Truth，不扩展全量数据集，不接入 Joern，不实现新的 CFG/DDG 引擎、Mock Generation 或 Behavioral Feedback。

实现阶段最终交付独立 V0.2 代码与 Prompt、测试结果、两案例实际可获得的轨迹与 Contract、质量/成本比较、实现报告和 Git 提交。报告明确工程验收结果、研究效果和未完成验证项，然后停止进一步开发。

当前阶段只交付本规格与已确认决策记录；未启动正式实验，也未完成实现。
