## Acceptance criteria

- [ ] 开始前冻结并记录模型及可得实际版本、输入身份、Prompt、代码、SDK/解析器、采样、限额、价格和重试策略；尽量保持共同配置一致。
- [ ] 计划两个案例×两个版本各一次，共 4 次有效运行；全轮最多 2 次技术故障重试，US$5 目标包含失败和重试；预算或故障限制优先，不保证凑足有效结果。
- [ ] 模型可用则 live；不可用则执行离线验证并明确原因和验证缺口。历史 V0.1 结果核对模型版本与运行条件后才可作正式基线，否则只作参照。
- [ ] 保存真实模型响应与实际工具调用轨迹，区分请求、执行、成功返回和有效 Contract；强制调用、宿主预调用与脚本回放不证明自主行为。
- [ ] 若两个真实案例均未调用工具，明确写“自主工具使用尚未验证”；可选诊断结果单列，不替代正式观察，不擅自增加 live 次数或预算。
- [ ] 按证据支持、条件/异常出口、依赖约束、过度推断、unknown/unresolved、新增分析事实及 Token/时间/费用逐案比较。
- [ ] 客观报告改善、无变化与退化，区分工程错误和模型局限；证据不足保留不确定性。不因质量差重试或反复调 Prompt，不据两个案例宣称普遍提升。
- [ ] 工程错误修复及重验保留原失败产物和配置身份；不覆盖 V0.1 代码、Prompt、历史结果或 Step 5B 证据。
- [ ] 按仓库实际配置完成回归及适用检查，明确无法执行的检查；独立审查实现是否符合项目标准及本规格。
- [ ] 实现报告分别给出工程验收、研究效果、live 自主行为验证状态和剩余限制；记录最终 Git 提交，停止扩展开发。

## Scope constraints

仅两个已审核案例；不访问 Ground Truth、不改 Stub-Tester、不接 Joern、不扩数据集、不实现 Mock Generation 或 Behavioral Feedback。质量不提升不阻塞工程交付，但未验证能力必须明确披露。

- [ ] 工程验收与研究质量评价分别给出结论，重点比较场景约束准确性、完整性、证据增量和推导错误；JSON/Validator 通过率只是工程指标，不作为质量评价替代。
