## 1. 问题与目标

Mock Spec 的研究目标是让 Agent 围绕测试场景主动探索仓库，发现有证据支持的部分依赖行为规格，
再通过反事实退化对照识别关键行为。

目前数据源选择正确：源码来自旧 Stub-Tester 中已审核的冻结快照。
但 Adapter 仅抽取预先指定的片段，SourceStore 仅保存这些文本，三个工具不能搜索快照中的其他文件。
例如 flask_308 当前只暴露 Masked Test、MUT 和导入片段；依赖用法工具不会自动查找被调用方法的实现。
因此，模型即使提出合理的探索需求，也无法发现初始输入之外的源码。

本轮目标：在同一份已脱敏冻结仓库内，打通“提出疑问 → 搜索发现 → 读取证据 → 更新判断 → 输出场景卡”，
保留单 Scenario Agent、三个只读工具和既定五步研究流程；允许自主多轮探索，不预设固定工具调用次数上限。

成功不以工具调用次数或字段填满衡量，而以真实模型能否按需获取新增证据、继续推理并输出可复核结果衡量。

## 2. 已确认的产品决策

- 探索对象是旧 Stub-Tester 的已脱敏冻结仓库，不是 Mockspec 自身，也不是运行后产生的归档 Workspace。
- 用户已确认冻结快照删除了隐藏答案。仓库访问以该准备侧脱敏结果为前提，不要求逐个源码片段再人工准入。
- 初始输入不是全部信息来源。Agent 可自主发现授权仓库内的普通源码、测试、文档及配置。
- 保持 OpenAI Agents SDK，模型名称固定为 `deepseek-flash`。
- 本轮不要求接入 SDK Sandbox 或 Docker；只读工具直接连接冻结仓库，由宿主实施访问边界。
- 后续生成、执行与修复阶段再接入 SDK Docker Sandbox，使用独立可写副本，冻结原件保持只读。

这里的“已脱敏”是本轮需求采用的输入前提，不将历史上对少量片段的审核记录改写为全仓脱敏实测证明。
新增案例仍须确认其属于正确的冻结输入协议和身份，不能回退到原始测试、参考答案或生成后归档。

## 3. 用户场景

Agent 从 MUT 与 Masked Test 识别最多两个候选场景，发现某个依赖的返回行为不明确。
它在冻结仓库中搜索该符号，读取实现、接口或相关测试，记录支持与冲突证据，修正候选场景。
随后推断当前测试所需的部分行为规格，尝试提出绕开目标场景的替代 Mock，并给出最小区分方式。
找不到实现、证据冲突或预算耗尽时，明确保留未知，不用猜测填补契约。

## 4. 范围

### 本轮包含

- 将授权冻结仓库连接到现有只读工具，支持搜索、读取与语法分析。
- 动态登记新发现的证据，并用于最终引用校验。
- 在现有控制器中保持共享预算、异常反馈及可复核轨迹。
- 使用真实模型完成一个案例的五步流程；通过后对三个代表性案例开展独立语义评阅。

### 本轮不包含

- Mock 代码生成、文件修改、目标测试执行或反馈修复。
- SDK 迁移、新增 Agent、增加工具数量或改变五步研究机制。
- 恢复快照中被隐藏或替换的实现；跨出授权仓库读取宿主依赖环境。
- 复制全量数据集、扫描或重算全量依赖哈希。
- 十个案例、每条件三次的 A/B/C 实验；该实验需等待语义评阅和生成执行闭环通过。

## 5. 功能要求

### 5.1 输入与仓库访问

宿主接收冻结 snapshot 身份、case ID 和对应仓库根目录，核对现有冻结协议、Masked Test 与任务身份。
初始模型输入保持 MUT、Masked Test、任务可见约束及逻辑仓库说明；不包含全仓文本、宿主绝对路径或控制记录。
仓库根目录由宿主绑定，模型不能另选根目录。

探索范围从“预先选定片段”扩展到“该已脱敏仓库中的允许文件”，保留已有 masking。
控制目录、外部评价材料、宿主凭据、其他案例与生成后归档不属于探索范围。
不能仅因文件不在旧 `reviewed_inputs.json.sources` 列表中就拒绝正常仓库探索。

### 5.2 三个工具

名称和数量保持不变；允许扩展参数，具体 Schema 在实现时确定，不以兼容旧参数为由阻止搜索能力。

| 工具 | 必需行为 |
| --- | --- |
| `inspect_source` | 支持按相对路径模式或文本关键词搜索文件与匹配片段；支持按发现的路径或 source_id 分页读取指定行范围 |
| `inspect_program_structure` | 对已发现文件或符号提供现有解析后端支持的结构、定义位置和语法关系 |
| `inspect_dependency_usage` | 支持围绕符号查询仓库内调用或使用位置；区分语法匹配、已解析目标与无法解析的关系 |

搜索返回相对路径、行号、匹配片段、截断状态和可继续查询的定位信息。
工具不得把文本同名匹配说成确定的调用解析，也不得把语法事实说成路径可行性证明。
不要求第一版实现完整跨文件静态分析；符号定位可采用有明确局限说明的搜索方式。
工具只读：不得导入或执行目标项目，不启动目标测试或仓库脚本。
解析器如需临时文件，只使用宿主临时目录，不写入冻结仓库。

### 5.3 证据登记与引用

`source_id` 用于稳定定位证据，不再充当预先穷举的阅读名单。
工具实际返回的源码片段进入运行级证据记录，至少保存：snapshot 身份、相对路径、行范围、原文及内容摘要。
只登记搜索发现的路径不等于已经读过文件内容；未返回给模型的源码不能被标为已观察证据。

最终验证器同时接受初始材料和本次探索得到的证据，严格核对身份、引用范围及原文。
同一文件分次读取应保持一致；检测到内容变化时明确失败，不悄悄混用不同版本。
身份校验复用已有冻结元数据，按实际读取范围留证，不通过重新计算哈希自动批准输入。

### 5.4 自主探索、终止与运行边界

Scenario Agent 根据当前测试目标和尚未解决的行为问题，自主选择需要查询的源码、接口、
调用关系和相关测试，并根据观察结果动态调整探索策略。

探索以任务相关行为规格的证据充分性为主要停止依据：关键约束已有足够支持、剩余不确定性
不影响场景选择，或进一步探索难以获得有效新证据时，Agent 可以结束探索。
停止时须显式说明证据支持、剩余未知及其影响、停止理由；不要求记录内部隐藏思维。
证据不足但难以继续获取时，允许以未知或无法确定结束，不得将“没有新证据”解释为规格已获证明。

Workflow Controller 负责安全权限、运行超时、Token 预算、重复探索检测及异常终止。
Agent 的正常停止与 Controller 的保护性终止分别记录，后者不能被标为证据充分。

- 宿主限制所有搜索和读取在绑定仓库内；拒绝绝对路径、路径穿越及符号链接越界。
- 搜索本身也必须遵守边界，不能先扫描外部内容再过滤返回结果。
- 不设置固定工具调用次数上限；失败、重试、分页和再次读取均完整记录，并计入实际资源消耗。
- 每次调用是一项有界搜索、读取或分析操作，不在工具内部隐藏多轮探索。
- 设置并记录搜索范围上限、单次超时和输出上限；受限结果明确标为不完整，不伪装成“没有证据”。
- 区分未找到、拒绝访问、不可解析、超时、输出截断、Token 预算耗尽和重复探索终止；错误作为观察结果进入后续判断。
- 时间与 Token 预算覆盖整次运行，不因阶段或工具重建而重置；模型请求数和工具调用数用于留证，
  不以 SDK turn 限制或模型请求次数上限变相恢复固定探索轮数。
- 重复探索检测结合规范化查询、访问位置和返回证据判断是否持续没有进展；正常分页、问题相关的
  查询调整及具有明确目的的复核不应仅因访问同一文件而被拒绝。检测策略与触发依据进入轨迹。

### 5.5 推理与产物

五步保持：理解测试目标 → 主动探索 → 部分行为规格 → 反事实退化对照 → Scenario Card。
场景卡需表达 scenario、evidence、dependency_behavior、key_behaviors（最多三项）、counterfactual、
discriminator、allowed_variations 和 unknowns；每项重要判断标记证据来源或假设性质。
这些是内容要求，不要求破坏冻结的 V0.1 Schema；现有契约与研究旁路记录需给出明确字段映射。

证据必须区分依赖契约、MUT 路径条件和测试目标。能触发分支不等于符合依赖契约。
允许最多两个候选、歧义、未知或无可靠退化候选。
本轮不执行替代 Mock，其通过状态只能是模型预测或未验证，不得标记为执行确认 PASS。

轨迹保存初始输入、模型调用与响应关联、工具参数和结果、证据登记、探索路径、候选变化、阶段状态、
资源消耗、重复探索检测结果及停止或失败原因；区分 Agent 主动结束与 Controller 异常终止。
不要求或声称记录模型内部隐藏思维；记录模型显式给出的判断依据即可。
失败运行也须保留已获得的轨迹；不得只有成功时才输出记录。凭据不进入轨迹。

## 6. 验收

| 层次 | 验收标准 | 不能据此宣称 |
| --- | --- | --- |
| 工具工程 | 能发现并读取初始片段之外的文件；路径越界被拒绝；超过六次的有效探索不因次数被截断；分页、动态引用、超时、Token 预算和重复探索检测有效 | 模型已经自主探索 |
| M2 真实闭环 | `deepseek-flash` 围绕案例中的实际疑问自主选择查询，获取新增相关证据，处理观察并完成五步及有效场景卡；轨迹可复核 | 规格或反事实语义必然正确 |
| 初步 M3 | 三个代表性案例分别评阅规格正确性、关键行为相关性、退化候选有效性和不确定性处理，逐项给出证据或缺口 | 方法优于 Direct 或提升故障检测能力 |

M2 案例应确实需要初始材料以外的上下文；不能通过指明工具调用顺序、答案文件或正确规格来制造成功。
初始材料足够时允许零次查询，但这种运行不能作为新增仓库探索能力的唯一验收证据。
EXTRACT 引用失败等已有阻塞必须保持可见并定位，不允许放宽原文校验来通过验收。

三个 M3 案例分别覆盖：目标明确且依赖简单、多种合理场景、原断言较弱且可能绕开目标场景。
评阅由独立于生成过程的人员或独立评阅流程进行；评价材料不回流给生成 Agent。
本轮未执行测试的判断均标为静态评阅，不能把推测计作实际故障检测结果。

## 7. 实施顺序与交付物

1. 对齐仓库级可见范围与现有输入身份记录，保留旧冻结基线及历史复现路径。
2. 在现有源码访问职责中增加有界搜索与读取，接通三个工具和运行级证据登记；不另造通用 Agent 框架。
3. 完成边界、预算及引用回归，再运行一个真实 M2 案例，保存可复现命令和完整产物。
4. M2 通过后进行三个案例的独立 M3 评阅，记录每步成功、失败与证据缺口。

交付：实现与针对性回归、一个完整 M2 轨迹、三份场景卡及独立评阅、未解决问题和复现入口。
若 M2 未通过，交付诊断轨迹和明确故障位置，不将阶段标为完成，也不推进方法实验。
实现时在原处更新 README 信任边界、architecture、usage、输入审核说明及契约字段映射；
本文作为需求基线保留，不成为第二份当前实现说明。

### 9.2 用户场景与成功定义

- Agent 选择一段已看到的源码作为证据，无需再次逐字输出其缩进、空行和全文。
- 宿主对选择核验后生成正式引用，调用者仍得到原格式的 ScenarioContract。
- 维护者能区分模型实际选择、宿主生成的引用以及最终验证结果，定位失败阶段。
- 验收者能判断新增证据是否确实影响了依赖约束或不确定性，而非只统计调用次数。

工程成功要求：所有阶段引用都通过相同的来源边界解析，精确文本由宿主生成，
非法引用选择仍失败，历史失败不被重新解释为成功。
M2 成功还要求：真实模型自主获取初始材料之外的相关证据、处理观察、说明停止理由，
完成五步并交付严格有效场景卡；允许歧义和未知，但不能用早停诊断替代完整交付。

### 9.3 功能需求

| 编号 | 需求 | 可观察结果 |

### 9.4 输入、输出与审计契约

模型的来源选择形状如下，示例仅说明字段，不为真实运行提供案例答案：

```json
{"source_id": "visible-source", "start_line": 10, "end_line": 12}
```

正式证据条目另外保留模型给出的 `id` 和 `rationale`，宿主只补充由该选择确定的 `quote`。
处理顺序为：解析研究输出 → 核对本次证据可见范围与身份 → 取出已观察原文 →
构造阶段标准对象/正式 Evidence → 执行原验证器。任何失败均不发布有效最终契约。
保持原有内容变化失效机制；不能从变化后的源文件重新取文以修补本次证据。

每个受影响阶段至少记录：

| 字段/材料 | 责任方与含义 |
| --- | --- |
| `wire_result` | 模型原始引用选择及语义字段；解析失败时保留可获得的原始响应与请求关联 |
| `result` | 宿主生成精确引用后的标准对象，仅成功解析时提供 |
| `citation_mode`、协议版本 | 宿主声明本次使用的引用表达方式 |
| 来源关联 | 初始材料对应输入快照；动态原文对应本次工具响应、观察记录和行范围 |
| 运行身份 | 宿主保存 snapshot/case/run 身份与证据摘要，不要求模型生成身份或哈希 |
| 错误信息 | 失败阶段、引用字段位置、source_id、行范围和失败类别；不泄露宿主物理路径或凭据 |

记录名的最终 Schema 必须在实现中固定并纳入测试，不建立并行的第二套审计文件系统。
历史产物不迁移、不覆盖；历史协议复现使用原提交，新验收不增加双控制器或自动降级路径。

### 9.5 案例适用性与准入

真实运行前，独立核对现有已审核案例并保存以下内容：

1. snapshot/case 身份、masking 与允许阅读范围的依据。
2. 至少一个影响依赖约束的具体待确认问题，以及初始材料不足的原因。
3. 允许的冻结材料中存在相关补充证据的依据；这是宿主评阅材料，不进入模型输入。
4. 选用或排除该案例的理由，是否需要接通已有 Adapter；不按模型多次运行结果挑选案例。

保留完整正常输入，不能为制造探索需求删减已有上下文。

若选中其他现有审核案例，研究入口只能按其明确身份接入已有 Adapter，
继续拒绝手工 task JSON、未审核案例及任意目录。若没有合适案例，
输出 `blocked_no_suitable_reviewed_case` 和所缺审核证据，停止真实请求。
这里的阻塞不妨碍独立完成引用协议与离线回归。

状态：独立设计审查通过（R0）；R1 工程已通过；R2 单次真实运行已完成，R3 未通过。更新：2026-10-27。

### 10.1 问题、证据与目标

表明：EXTRACT 已能用 locator 形成精确引用，模型也自主查询了父类；但评估回执时
多出 `attempt_sequence_note: null`，被严格拒绝，下一次读取没有执行。
[独立接口诊断](../out/staged-inference/issue17-response-conformance-20261026/report.md)
确认实际 HTTP 请求保留严格 Schema；单次合成对抗请求合规，未定位原违规的确定原因。

产品问题有两项：轻微表示错误会中断整个研究流程；候选描述把未知 slot 内容写成
确定的 Mock 配置，混淆依赖约束与隐藏答案恢复。目标是让可证明语义未变的有限表示错误
有一次显式纠正机会，并让候选以条件假设表达；不承诺任意模型错误都能恢复或一次 M2 成功。

第 10 节实施前的代码依据（历史问题状态，后续实现见本节末尾）：

- [QuerySelection / QueryAssessment](../experiments/staged-inference/controller.py) 的两个
  QUERY 嵌套字段为 raw `Any` 加供应商 Schema，本地严格校验在 QUERY 循环后进行。
- 同文件 `_call_stage` 和 `BudgetHooks` 保留失败响应与调用记录，但 SDK 解析失败时
  QUERY 循环尚未登记 stage/attempt；收紧类型必须同时保留这条失败留证路径。
- [QueryExecutor.register/reject/execute_registered](../experiments/staged-inference/query.py)
  分别负责登记、拒绝及实际派发。原无效尝试不能被覆盖成成功记录。
- `_deliver_with_repair` 只处理 DELIVER，依赖已确认的完整契约语义快照；不能直接用于 QUERY。
- [格式修复测试](../tests/test_staged_format_repair.py) 已要求严格语义相等、引用失败不修复、
  失败不再重试；[QUERY Schema 测试](../tests/test_staged_query_schema.py) 当前显式允许 raw 畸形对象供计数。

### 10.2 范围与替代方案

仅修改研究控制器、研究 QUERY 账本接入、对应合成回归和当前说明。

| 方案 | 收益 | 代价/判定 |
| --- | --- | --- |
| 保持所有格式错误直接失败 | 最少改动，原始结论清晰 | 无法改善本次表示错误中断；保留为默认拒绝分支 |

第 9 节引用失败不修复、无质量重跑、无隐藏读取和语义判断独立核验继续有效。

### 10.3 输出职责与假设表达

   绑定后由宿主补号，再形成内部对象。不能删除内部关联编号或把补号记成模型原始输出。
3. 新 policy、prompt、record 版本升至 v0.3；其他未变的阶段 wire 保留其已定义版本。

   或 VERIFY 原文；候选中的未证实行为写为“若…则…”假设，缺少依据时列入 unresolved。
   imports、测试名或最终断言不能单独证明隐藏配置或验证次数。
5. 发现支持或反驳应指出所获行为事实；仅找到 import、字段或构造参数，尚未确定行为时
   使用 `no_new_information` 并说明剩余缺口。类型检查不证明该判断正确，仍须独立语义评阅。
   不新增针对 CloudFoundry 的答案、路径、用例分支或关键词打分规则。

### 10.4 QUERY_FORMAT_REPAIR 的唯一允许范围

原响应始终先判无效并保存；仅当以下条件**全部满足**时，允许请求一次模型格式纠正：

- 由现有 BudgetHooks 保存的 output 中，取得唯一 message，其 status 必须明确为
  `completed`，content 仅有一个 output_text；其余 output 只能是独立 reasoning 项。
  不接受缺失完成状态、第二条最终文本、工具调用、混合 content、refusal 或截断标志。
  不假设未保存的 provider 顶层状态，也不修改生产 hooks；用 `decode_json` 拒绝重复键。
- 唯一一类校验错误是 `/previous_receipt_assessment/<未知直接子字段>` 的
  `extra_forbidden`，且这些字段的值全部严格为 JSON null。字段名不能是已移交宿主的
  `attempt_sequence`；旧协议版本也不属于格式错误。其他路径/值均不进入修复。
- 所有规定字段已经齐全、类型正确；decision/attempt/stop 的组合合法；有且仅有本轮
  待评估回执。候选 ID、工具名、参数 JSON 和参数形状已通过无 I/O 的原校验逻辑。
- 已存在的所有来源、行范围、停止证据通过原 SourceStore 校验；来源失效、未观察或
  错误引用直接失败，不能通过修复请求补读。任何身份、预算、用量或超时问题也不进入修复。
  此处“未观察”限制已有证据引用，不要求下一次拟议读取的行已被观察；拟议读取只核对
  参数形状与本轮已登记的来源身份，不预读或拼接完整源码。仓库中的离散搜索命中可
  建立来源身份，后续新行仍须由正常工具派发取得；片段模式沿用已知输入范围限制。
- 本轮尚未消耗全局格式纠正名额，剩余共享时间/token/费用门禁允许一次调用。

**语义保持判据：**宿主构造仅用于比较的快照：从完整 raw QUERY JSON 移除上面已经
确认的未知 null 字段，除此以外保留所有值；投影必须通过严格 v0.3 类型及原业务校验。
这份投影不是接受结果，不派发工具、不填入 stage.result、不作为最终模型输出。
同时冻结 pending receipt 的 case/run、sequence/response_id 与规范化内容摘要。

模型必须重新返回完整 v0.3 QUERY 对象。严格校验通过后，其全部规定字段必须与快照
相等：decision、完整 query_attempt、assessment 的 impact/rationale、外层 impact、
stop_explanation 及其证据/未知项。JSON 对象键顺序不敏感；列表顺序、文本、数值类型
严格保持，尤其 `arguments_json` 字符串不重排、不 trim、不转换。
不会用自然语言相似度代替相等，也不能把“合理的新判断”视作格式纠正。

修复输入只含原无效 QUERY、允许错误的位置与错误类型、比较快照和通用保持规则，
不提供新源码、工具或案例评阅答案。原槽位内容未知的问题不能通过这一步解决。
修复后 pending receipt 仍须匹配冻结身份/摘要，SourceStore 仍有效；通过后才允许继续。
无法获得完整 raw JSON、任何非 null 额外字段、缺字段、错类型、错关联、参数或引用错误、
修复仍不合法/改变语义，全部终止；不进行第二轮纠正。

### 10.5 状态、预算和账本

新协议整次运行的**格式纠正总名额为 1**，由 QUERY_FORMAT_REPAIR 与现有 DELIVER
FORMAT_REPAIR 共享，而非每个 QUERY 各一次。名额在准备发送纠正调用时预留并不恢复；
网络失败、预算拒绝或取消都不能重新领取。实际请求数由原 UsageLedger 记录。
DELIVER 的原允许错误和精确语义校验不扩大；若 QUERY 已用名额，后续无效 DELIVER 直接失败。

整次运行创建一个共享 allowance，QUERY 和 DELIVER 接收同一实例。
其状态只允许 `available → reserved`：通过结构/语义资格检查后，在进入 `_call_stage`
前原子预留；之后只附加成功/拒绝/失败结果，不退回 available。
进入前已知无剩余预算或用量未知则直接停止，不发送请求；预留后若 UsageLedger 的
预发送门禁拒绝，请求数仍为 0，名额仍已消耗并记录 `blocked_budget`。
“没有付费请求”与“未预留过纠正名额”必须分别统计，不能据零请求数自动恢复名额。

所有纠正调用使用同一 deadline、UsageLedger 和费用门禁，`max_retries=0`；
用量未知立即停止，不刷新预算或无进展计数。保留原输出长度/阶段超时上限；
格式纠正并非新语义样本，不允许再次 EXTRACT、再次完整 QUERY 推理或重跑整例。

执行状态顺序固定为：

1. 保存 raw 响应与模型调用；即使 SDK 严格解析失败，也从唯一最终文本登记无效 QUERY
   stage。只有经 `decode_json` 得到 JSON object，且 `decision == "request_query"`
   或 `query_attempt` 键存在且值非 null 时，才以 raw query_attempt（缺失则为 null）
   调用 `register` 恰好一次，并 `reject` 为 `protocol_error`；与当前登记谓词保持一致。
   投影和资格检查不得再次登记。不能可靠取得 JSON object 时只保存 stage/原响应，
   不从文本猜测工具尝试；`finish_queries + query_attempt=null` 也不登记。
2. 检查修复资格并冻结比较快照及 pending receipt 身份。无效原尝试记录保持不变。
3. 有资格且预算允许时记录 `QUERY_FORMAT_REPAIR` 并调用一次；无工具、无源码读取。
4. 原严格校验及快照相等后，记录新的纠正响应。若仍请求查询，登记**新的**尝试并关联
   原尝试/repair，使用下一 sequence 并照常消耗原 attempt budget；仅该新尝试派发一次。
   原尝试永远保留 `protocol_error`，不借恢复退回预算。finish_queries 不捏造工具尝试。
5. 修复失败终止，原 attempt 不改成成功；修复次数、模型请求数、已登记工具尝试数、
   实际派发数分别留证。协议拒绝和纠正调用不计为新增源码证据，也不重置无进展保护。

沿用现有 `format_repair_log`，新增 stage/category、原调用序号，以及确定的关联字段
`original_attempt_sequence`、`repaired_attempt_sequence`、`repair_call_sequence`；
没有 attempt 的 finish 分支前两项为 null，未进入纠正调用时 repair_call_sequence 为 null。
另外记录错误位置、资格判定、raw before、comparison_snapshot/hash、pending receipt
身份摘要、raw after、结局、全局名额使用与预算拒绝原因；无资格和名额已耗尽也留证。
模型原始响应、宿主关联编号、宿主生成 quote 分开记录，不另建平行账本。

| 显式受控终止 | [run](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/src/minisweagent/agents/default.py#L88-L124) 与 [完成信号检查](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/src/minisweagent/environments/local.py#L45-L55) | 保留 Agent 正常停止与 Controller 保护终止的区分；另加本研究所需的问题/证据一致性检查 |
| 有界反馈与原始留证分开 | [观察模板](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/src/minisweagent/config/mini.yaml#L112-L149)、[观察消息](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/src/minisweagent/models/utils/actions_toolcall_response.py#L107-L140) | 精简模型输入，完整审计数据留在原记录；不能把截掉的原文当作已观察证据 |

mini 核心不提供专门的行为问题账本、证据充分性证明或全历史自动摘要。
下面的问题状态是本研究的最小补充，不声称由 mini 实现或验证。
不照搬它的开放 bash、必须调用工具的响应协议或完成哨兵；这些不能替代本项目的证据准入与停止理由。

Token 调研依据：OpenAI [reasoning 文档](https://developers.openai.com/api/docs/guides/reasoning)
说明其输出上限同时约束可见输出与推理 Token，usage 可报告 reasoning 明细。
本项目固定 `openai-agents==0.24.0`，调研环境的 `openai` 为 `3.35.1`；
该 SDK 的 `agents.usage` 会把缺失的 reasoning 明细正规化为 0，
`agents.items.ModelResponse.raw_usage` 才可能保留供应商原始字段及其存在性。
`on_llm_start` 在模型调用之前，`on_llm_end` 需要已返回 ModelResponse；
异常前没有完整响应时不能假定 hooks 或 RunResult 能补回全部信息。
版本以 [pyproject.toml](../pyproject.toml) 及实施时记录的实际安装版本为准。
这些 OpenAI 行为不能自动推广到 `deepseek-flash` 的兼容服务；支持与否及缺失字段必须显式记录。

### 11.3 工作包 A：QUERY 自主探索可靠性

#### A1. 宿主呈现实际能力

在现有 QUERY payload 中增加紧凑能力视图，由真实运行配置/Store 绑定生成，不由模型猜测。
以下为逻辑字段合同，具体 DTO 名称可随代码约定调整，信息不得遗漏：

| 信息 | 必须表达的内容 |
| --- | --- |
| 访问模式 | `snippet` 或 `repository`；搜索是否可用，不得宣称未启用的能力 |
| 初始材料 | 初始 source_id 与实际可见行范围；明确这只是起点，不是仓库全部文件清单 |
| 可探索范围 | 当前绑定的审核仓库逻辑范围、现有 search/read/analysis 能力及通用限制；不暴露物理根目录、宿主准入记录或准备侧答案 |
| 已发现/已观察 | 路径发现、实际返回的搜索匹配行、已读取行分别表示；发现路径不授权全文引用 |
| 工具用法 | 一个与真实参数验证一致的通用搜索/读取示例；不包含真实验收案例的答案路径、符号或调用顺序 |
| 本轮状态 | 待评估回执、工具错误/分页/截断、已有保护性进展状态；预算若展示须为宿主事实，未知不能显示为零 |

保持原三个工具及无副作用参数验证；结构/用法分析不自动增加 observed 原文。
不扫描全仓生成文件目录。能力视图不复制完整回执或源码，不创建第二份 SourceStore。
片段模式继续按现有范围运行；不以仓库模式能力说明误导片段模式。

#### A2. 持续维护行为问题与证据缺口

复用 EXTRACT.unresolved、QueryAttempt.question、回执 assessment 和停止 remaining_unknowns，
在控制器现有运行记录内维护一份紧凑问题状态，不建独立服务或持久记忆系统。

- 进入 QUERY 时，宿主为每条 EXTRACT.unresolved 按原顺序分配运行内稳定 question_id，保留原文与来源；
  默认标记 unresolved/阻塞，模型可显式说明其为何不影响当前部分规格。EXTRACT 没有未知项时允许空集。
- 模型可提出新的行为问题，宿主分配 ID；既有问题只能按 ID 更新，不得通过整表覆盖或空列表删除。
  问题可以关联一个或多个现有候选；无法归属时保留为任务级问题，不强行指定候选。
- 每项保留：question、candidate_ids、status、blocking、当前证据 locator、显式理由及相关回执关联。
  status 为 `unresolved / partial / resolved / nonblocking`；resolved 表示**模型声明已解答**，不表示宿主证明。
- resolved 必须给出已观察引用与简短行为结论；nonblocking 必须说明不影响哪项场景选择/约束，
  不能删除问题。partial 保留未解部分；resolved/nonblocking 可因冲突观察重新打开。
- 每个查询关联一个既有或本轮新问题；回执评估与问题更新一起校验后提交状态。
  宿主沿用唯一 pending receipt 绑定，模型不能伪造尝试序号。保持第 10 节的评估两字段约束，
  问题更新放在研究 QUERY 的独立字段，不把旧 receipt ID 放回 assessment。
- 没有新增有效原文的工具错误、未读路径或分析定位不能伪装为新行为证据。
  初始材料也可解答问题，因此不强制为关闭问题而调用工具。
- 每轮只传当前状态、必要的观察/回执上下文；完整更新及其 model_call/receipt 关联留在现有 record。
  保留相关冲突观察和未完成评估，不借摘要删除反证。无需记录内部隐藏思维。

本包不让宿主从自然语言自动推导正确答案，也不加入案例关键词规则。
任一未知 ID、跨运行关联、未观察引用或状态组合错误，原输出无效，不能先更新状态后校验。

**问题事务 wire 的唯一约定：**保留 QueryAttempt 的既有工具参数形状；在新版本
QuerySelection 顶层增加 `new_questions`、`question_updates`、`query_question_ref`。
`new_questions` 是有序列表，每项只有 question/candidate_ids；初始状态为 unresolved/阻塞。
问题引用统一为 `{existing_id: string|null, new_index: int|null}`，两者必须且只能一个非空；
new_index 是本响应 new_questions 的零基下标，不是跨轮 ID。
`question_updates` 每项包含 question_ref/status/blocking/evidence/rationale，不允许重复更新同一项。
request_query 必须有 query_question_ref，finish_queries 必须为 null；QueryAttempt.question
仍表达此次具体查询目的，不承担身份键。stop_explanation.remaining_unknowns 的新 wire 每项
增加同型 question_ref，其他 question/impact/blocking 语义保留；question 必须与所指问题原文一致。

宿主按运行内递增序号分配正式 question_id，将 new_index 映射到该 ID 并记录映射；
模型下一轮只看到正式 ID。resolved 必须 blocking=false 且有有效证据；nonblocking 必须
blocking=false 且有影响说明；unresolved/partial 保持 blocking=true，降低阻塞性必须显式转为 nonblocking。
剩余未知必须恰好覆盖最终暂存状态中所有非 resolved 问题；不允许重复、遗漏或捏造。

先在临时副本验证创建、更新、pending assessment、引用及 stop 一致性，全部通过再一次提交
问题状态和回执评估，之后才派发工具。失败不提交问题状态、不消耗正式问题 ID，也不派发。
**尝试审计不回滚**：原第 10.5 节的登记谓词仍在业务校验前恰好登记工具尝试；
无效请求保留 protocol_error 并正常消耗原尝试预算。不得为了问题事务原子性删除失败尝试。
格式纠正仅比较完整原始事务（含 new_index），不提前分配/提交问题；修复后按同一规则验证。

#### A3. 有依据的 finish_queries 检查

停止检查只消费已有状态，不发起读取或额外模型调用。
先完成本轮 pending receipt 的评估和问题更新，再检查 finish；保留原输出及确定的拒绝原因。

| 停止理由 | 机械前提 | 允许的结果含义 |
| --- | --- | --- |
| `evidence_sufficient` | 有有效观察引用；所有已登记问题均已解答；无剩余未知或阻塞项；每项关闭都有可追溯依据 | 可以进入 CONSTRUCT；不自动得到 SELECTED 或语义通过 |
| `unknowns_nonblocking` | 有有效观察引用；仍未解答的问题全部显式为 nonblocking，理由完整；remaining_unknowns 与问题状态一一对应 | 可构造有限的部分规格；不能把非阻塞未知写成已证实约束 |
| `no_further_evidence` | 剩余问题及影响完整保留；逐项给出停止获取证据的原因，关联已有搜索/读取失败或实际能力限制 | 可以进入 CONSTRUCT 表达部分知识与未知；有阻塞项不得 SELECTED，按原校验产生 INCONCLUSIVE 或合法 AMBIGUOUS |

`no_further_evidence` 的依据至少区分：已尝试但未获行为证据、访问被拒绝、能力确实不可用、
仍有未尝试方向但模型判断收益不足。最后一种必须标记“未探索”，只能保留不确定性，
不能声称仓库已搜索穷尽。仅“初始 sources 未列出”不能作为不可访问的结构化依据；
不得用正则分析自由文本假装检测所有同义错误。零查询若有真实能力限制可以不足停止，
但不满足 M2 的新增相关证据条件。

合理零查询：初始证据已足以支撑所声明的部分规格，且通过上表一致性检查；允许构造。
错误早停分两层：

1. **协议可检测**：未处理阻塞问题、遗漏问题、无依据关闭、未完成回执评估、虚构引用、
   能力标记与停止理由矛盾。拒绝 finish，记录 `output_invalid`/具体检查码，不进入 CONSTRUCT。
2. **语义才可检测**：模型完整填写协议，但引用不支持结论、错误标为 nonblocking 或遗漏了本应识别的问题。
   由隔离的离线语义评阅及真实 M2 评阅判失败；不能承诺宿主完整识别，不将格式通过计作充分性证明。

本包不新增语义纠正重试。finish 被拒绝后沿用原无效输出终止路径；第 10 节仅允许的 null-only
格式纠正仍按原精确语义快照运行，快照必须包含新增问题状态字段，不能借修复改变停止结论。
正常查询循环仍可据观察主动调整和继续；不设置最小查询次数或为了验收强迫搜索。
超时、预算、无进展、身份变化及取消保留 controller/caller 归属，不转写为 Agent 正常停止或成功规格。

#### A4. 独立验收矩阵

| 编号 | 合成输入/行为 | 预期可验证结果 |
| --- | --- | --- |
| A-01 | 同一合成任务分别绑定片段/仓库模式 | 实际 SDK 输入准确显示能力；无宿主路径/审核答案；初始清单不被声明为仓库全集 |
| A-02 | 初始材料完整，支持合法零查询 | 0 次工具尝试及派发，停止检查通过，原正式校验有效；单独标记不满足 AC-17-10 |
| A-03 | 留有阻塞问题却声明充分；或未引用即关闭/删除该问题 | 停止被拒绝，无 CONSTRUCT 请求、无最终契约；不靠强制一次查询实现 |
| A-04 | 协议完整，但仅 import/字段声明被当作行为依据 | 独立语义夹具判失败；报告明确机械检查可能通过，不添加案例正则冒充推理验证 |
| A-05 | 初始不足，自主请求的合成轨迹依次得到声明、行为原文、冲突信息 | 问题跨轮保留，partial→resolved→重新打开可追溯；每次更新绑定正确观察 |
| A-06 | 搜索无结果/拒绝/不可解析/截断/仍有未尝试方向，模型不足停止 | 区别原因，保留未知和影响；阻塞项不得 SELECTED，正常不足停止与保护终止分开 |
| A-07 | 仅发现路径、稀疏命中间的未读行、跨运行 ID、引用变化 | 原引用边界继续拒绝；检查阶段零隐藏读取 |
| A-08 | 正常分页、新证据、持续重复、共享预算耗尽与取消 | 原进展/保护测试通过；保护性终止不发布契约、不重置计数或预算 |
| A-09 | 新问题字段出错，或通过 QUERY_FORMAT_REPAIR 改写问题结论 | 严格 Schema/修复快照拒绝；原 null-only 和单次共享 allowance 回归保持有效 |

A-02/A-04/A-06 的语义预期包含可核查源码与判定理由，由独立 reviewer 核对；
评阅材料不注入 Agent 输入。脚本模型验证控制流程，不证明真实模型已学会停止。

### 11.4 工作包 B：CONSTRUCT 输出可靠性

#### B1. 先测量，再去除重复上下文

先用固定合成输入及已有失败请求的**只读副本**形成前后测量，保留旧证据不变。
分别统计指令、实际发送 Schema、payload、源码文本与回执的 UTF-8 字节；Token 估算注明算法，
不把 byte/4 估计或 JSON 长度当供应商实测。B 的测试可以使用旧 QUERY 的有效停止结果，
不要求先完成 A；与 A 的衔接只消费经过验证的问题/停止状态。

CONSTRUCT 专用输入投影要求：

- 初始 masked test、MUT 和原支持片段保留一次精确带行号原文；删除与之重复的整段文本表示。
  保留任务可见约束、原目标依据、候选及缺口，不能只有 source_id 而没有解释结论所需的源码。
- 查询得到的原文按 source_id/行号去重；保留原始坐标、空白、非连续空洞、冲突证据。
  同一坐标文本不同直接失败，不拼接虚假的连续片段、不读 Store 尚未观察的行。
- 回执只传判断所需的请求问题、执行状态、观察引用、assessment、未完成项及必要的分析事实；
  raw 响应、重复 quote、内部散列及审计元数据保留在宿主 record，不多份塞入模型输入。
- 能力、问题状态、stop 与 EXTRACT 中相同事实引用一次即可；不得在投影中推断新的行为结论。
  记录投影版本、输入散列、源记录关联和去重规则，审查者能复原模型实际看到的材料。
- 不做按“看起来不重要”删除原文的语义压缩，不按百分比截去证据。若仍过大，明确预检失败，
  或使用事先登记的 B4 分片方式；不把缺失文本隐藏在正常输入中。

#### B2. 模型与宿主输出职责

优先缩小研究 wire，不改正式契约及内部验证语义。所有变更必须有新 wire 版本和字段映射测试。

| 内容 | 责任 |
| --- | --- |
| 正式 schema_version、case_id、language | 宿主从本次已验证任务/固定协议补入；模型不重复生成；不得跨任务复用 |
| quote、回执关联、用量、调用与证据身份 | 宿主沿用已观察原文与既有记录；quote 已经由宿主生成，不将既有能力计作新收益 |
| 原目标的文字化、候选条件、依赖约束、状态选择、证据选择及 rationale | 模型判断；EXTRACT 仅有目标 locator，不能由宿主把它当已完成的目标语义文本 |
| 关键行为、角色/依据映射、允许变化和未知项影响 | 仅保留现有 CONSTRUCT 字段的模型责任与严格映射；重复内容可通过显式索引引用，不能由宿主猜测语义相等 |

保持最多两个候选、最多三项关键行为；一次表达一个主张，证据使用 ID/locator 引用，
不在不同说明字段复述整段代码。必要的条件、参数关系、返回/异常、状态影响、反证和未知不能删除。
明确非必需集合可为空；不能为减少长度把原必需字段改成可缺省，或用固定模板补语义字段。
新 wire 经确定性组装恢复完整 `ConstructResult`，随后执行原 `_validate_constructed`、
`validate_contract`，并继续原 CONTRAST/REVISE/DELIVER 及精确语义保持检查。
保存 wire_result 与宿主 result、补入字段来源；正式有效不等于语义正确。
反事实及区分观察仍由后续 CONTRAST 生成；本包不向 CONSTRUCT 添加反事实字段或提前生成要求。

#### B3. 推理 Token、截断与失败留证

每次阶段调用记录实际输出上限、有效配置、输入/输出/总 Token，以及供应商可提供的 reasoning 明细。
每个数值带存在性/来源：`reported`、`not_reported` 或 `unavailable`；后两种值为 null，
不得把 SDK 默认 0 当供应商明确报告 0。推理 Token 若已包含在 output 中，不再次计入总量或费用。
缺少 reasoning 明细但 input/output 计量完整，不因此单独阻塞；缺失整次调用用量则保持原未知用量门禁。

已知失败只证明触及输出限制；是否为推理消耗、可见 JSON 过长或供应商转换问题，分别标为
已报告事实、待验证解释。没有原始明细不能补算历史 reasoning Token，也不能声称知道第三次费用。
只记录可得计量与显式说明，不要求获取模型内部思维。

失败记录覆盖实际 SDK/provider 边界，而不只依赖成功返回的 Runner 结果：

- 对完整/不完整/拒绝响应，尽可能在严格输出解析前保存已收到的脱敏原始响应、response/request
  关联、status、incomplete_details、usage 与正文片段；不得记录请求授权头或凭据。
- 已核对固定 SDK 的 `OpenAIResponsesModel._fetch_response` 在 `responses.create()` 返回后，
  对 failed/incomplete 抛错；`models._response_terminal.response_terminal_failure_error`
  只保留格式化说明，没有附带完整 response，故不能以异常对象提取作为实现方案。
  **采集接点固定为本次运行 AsyncOpenAI 客户端的 HTTP response hook**：通过既有
  `DefaultAsyncHttpxClient(event_hooks=...)` 注入，非流式响应先 await aread，再保存脱敏的
  响应体及允许的请求关联字段，供原 SDK 继续正常解析；不消费/替换返回内容，不采集授权头。
  按本次顺序调用的 model_call sequence 绑定，不建立全局 hook；本包不切换 streaming。
  hooks 的成功响应记录与该原始响应按调用/response ID 关联，不能重复增加共享账本用量。
  失败 usage 归入本次失败调用及整次用量汇总，沿用原账本/报告出口，不产生第二份计费状态。
  客户端创建归 run.py；采集/关联逻辑归研究控制器的调用记录职责，不修改生产或全局 SDK。
- MockTransport 已返回完整响应却没有留存原文/usage 时，B-05 和 D1-B **失败**，不能用
  capture_unavailable 过关。网络未返回、超时/取消导致正文不完整时，允许记录
  `capture_unavailable`、捕获位置和原因，整次失败且用量未知；明确拒绝继续请求。
  若采集本身序列化/写入失败，仍终止该阶段并报告采集失败，不能退化成正常成功。
- `response.incomplete`、截断或缺少完整结构时，即使片段是可解析 JSON，也不得物化为有效契约、
  进入语义格式修复或继续下一阶段。已有片段仅作失败诊断；不请求“接着写”拼接成功结果。
- 记录开始、返回、解析结果和计量是否完整；start hook 不等于远端已执行成功。
  已知小计与整次未知量分开；不能重复计费，也不能因为采集到失败 usage 就把失败记为成功。

#### B4. 条件式阶段预算与增量构造

默认先实现 B1–B3，仍为单次 CONSTRUCT。阶段预算/分片不因本 PRD 自动启用。
启用决策须附测量和理由：去重后的输入、实际 Schema 与完整合成输出规模、已有供应商计量、
预测误差和无法判断之处。脚本模型不会复现真实推理 Token 消耗，不能宣称它证明新上限足够。

1. **阶段级预算**：若需要，为 CONSTRUCT 提供显式 output cap 覆盖；缺省沿用原全局 cap。
   有效 cap 写入实际 SDK 请求及调用记录，发送前预算估计也必须使用同一值。
   所有请求仍共享原绝对 deadline、总 token/费用及格式纠正名额；不能仅改变 SDK 参数绕过门禁。
   不把 reasoning_effort 当精确 Token 上限；兼容服务未证实支持的参数不发送。
2. **增量构造**：只有完成上述减负仍有明确容量风险且单次预算调整不合适时，才在首次真实运行前
   固定分片合同、调用上界和测试。子调用属于 CONSTRUCT 内部，不新增研究阶段；分片本身不触发
   QUERY。若构造内容暴露会实质改变规格的证据缺口，则按后续 ADR 的语义补查通路处理。
   各片先用严格类型校验并绑定同一任务/证据快照，宿主只做确定性拼装；完整结果再过原校验。
   不允许两片覆盖同一语义字段、自动选一个冲突值或由额外模型“合并猜测”。
   任一片缺失、截断、冲突、预算不足或取消，整阶段失败，已成片不得发布为最终契约。
   该选择的具体分片 Schema、顺序和最大调用数是启用前必交付设计；未确定则禁用分片，不阻塞默认单次方案开发。

不在一次真实运行中发现截断后临时切换预算/分片或追加重试。任何启用项须有独立负向回归，
进入预登记协议；若最后一次 M2 仍失败，保留失败并另行判断后续，不连续抽样挑成功结果。
